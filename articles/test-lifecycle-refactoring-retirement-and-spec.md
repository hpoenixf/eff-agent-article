# 测试也会过期：把重构、退役和删除前移到 Spec

头像上传原来只支持 JPEG，现在要增加 PNG。实现刚改完，一条旧测试失败了：“上传 PNG 应当被拒绝。”

为了让测试重新通过，把实现改回只支持 JPEG，会丢掉新需求。直接删掉整组格式测试，又可能连“伪装成图片的文件不能上传”也一起删掉。

下面用这个教学模拟说明，业务、文件和情节均为示意。它要回答的是：**需求改变时，旧测试保护的要求是否还有效？有效的继续守住，被替代的及时调整，只服务旧机制的检查则考虑退出。**

这些决定最好在写设计和规范时作出，而不是等实现结束，再围着红灯逐条猜。

## 一、失败之后，先找行为依据

一条测试失败，可能是实现有错、测试前提有错，也可能是需求有意改变。先检查实际差异，再查本次获准的行为约定。

在头像案例中，需要明确的不只是“支持 PNG”，还包括：原来的 JPEG 继续可用；真正能解码的 PNG 可以上传；既有文件大小限制和用户隔离继续有效；伪装扩展名、损坏内容仍被拒绝。

于是，旧的“PNG 一律拒绝”被新要求替代，其他保护没有失效。

如果找不到这项需求依据，不能因为实现现在允许 PNG，就反推测试应该允许。实现与测试互相对照，仍需要独立的产品承诺。

ETF Agent 清理测试时，也遇到过类似冲突：当时的恢复约定允许先列出执行占用记录已经缺失或到期的任务，进一步检查，旧断言仍把其中一部分排除。记录到期不能证明原执行者已经停止。调整测试时，需要同时保留“正在执行的任务不被干扰”和“列入候选不等于获准恢复或修改”的保护。这个真实教训说明，更新一个允许条件，并不意味着放松后续准入。

头像案例把同一判断放到了更熟悉的场景：允许新格式，不等于任何标成 PNG 的内容都可信。

## 二、不要整组删除，逐项看它还保护什么

先把原有测试按行为展开，处置会清楚得多：

| 旧要求 | 本次怎样处理 | 原因 |
| --- | --- | --- |
| 合法 JPEG 上传成功 | 保留 | 新需求没有取消 JPEG |
| PNG 一律拒绝 | 替换为合法 PNG 可上传 | 产品支持范围已经改变 |
| 扩展名像图片，实际内容无效时拒绝 | 保留，覆盖新格式 | 新增格式不能绕过内容检查 |
| 文件超过既有大小上限时拒绝 | 保留 | 格式变化没有改变容量承诺 |
| 用户只能改自己的头像 | 保留 | 格式变化没有扩大操作权限 |

补充的 PNG 正例应该经过真实上传入口，再读取保存结果，确认图片能被打开。只检查后端函数返回成功，可能漏掉页面仍只接受 JPEG 的限制。

负例也要有辨别力：把一份无效内容改名为 PNG，应当继续失败。有效 PNG 与伪装 PNG 放在一起，才能检查新允许路径和旧保护是否同时成立。

预期结果来自事先准备并核对过的样本，不能调用被测解码器给自己生成“正确答案”。测试应该有机会抓到实现的错误。

## 三、已有测试，不只有保留和删除两种选择

按当前行为判断，常见的去向有五种：

| 去向 | 适用情况 | 头像案例中的动作 |
| --- | --- | --- |
| 保留 | 仍保护有效要求或独有反例 | 保留跨用户修改被拒绝的检查 |
| 重构 | 要求有效，但测试锁定了内部写法 | 从断言私有解码函数名，改为检查合法图片的上传结果 |
| 合并 | 多处重复证明同一行为 | 共享无状态样本准备，合并重复装配，保留各格式独有反例 |
| 退役 | 旧实现正在退出，仍有实际依赖 | 旧图片库相关检查随迁移保留到明确退出点 |
| 删除 | 完全重复、没有有效要求，或退出条件已满足 | 删除只要求旧函数必须存在的过期断言 |

Google 的 Andrew Trenk 在[《Test Behavior, Not Implementation》](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html)中讨论了测试对外行为的好处。内部解码器换了名字，头像上传承诺不变，行为断言通常不应跟着失效。

但调用顺序也不能一概当成实现细节。“保存成功之前不能向用户报告成功”，就是用户依赖的行为。如果测试独占保护它，应当继续保留。

合并同样不能只看层级。一条页面测试虽然经过更多模块，未必检查跨用户修改，也未必能制造损坏文件。能否替代，要看它是否仍能发现原来的独有故障。

删除不必机械地一删一补。没有现行要求的重复断言可以直接退出；仍保护隔离、持久化或其他必要行为的反例，则先落实等价或更强的覆盖。

## 四、旧库已经迁走，迁移检查还要跑多久

假设头像处理曾使用旧图片库。迁移期间，扫描依赖和调用点，确保没有漏接线，很有帮助。

迁移结束后，如果每次普通回归还要遍历整棵源码，检查旧包名、旧类型和旧文件名，就应重新判断它保护的是什么。

ETF Agent 退出 LangGraph 运行层后，也清理过类似的退役扫描。当时核对了依赖、生产接线与现有行为测试，再移除只服务迁移的扫描，没有为了维持它继续建设更复杂的解析器。历史身份和仍需读取的数据并未因名字相似而一起删除。

回到头像系统，可以在原迁移任务中写明：新请求不再调用旧库；仍需读取的历史头像可用；必要行为已有当前入口的检查；旧格式没有尚未处理的真实消费者。满足条件后，删除只服务旧库退出的活动检查。

如果某个扫描仍独占保护有效的架构约束，可以继续保留。退出条件是让人重新判断，不是规定所有静态检查都会过期。

同样，注释里出现旧包名，不等于运行时仍依赖旧库；删除了测试，也不证明迁移已经完成。依赖事实需要独立核对。

## 五、把处置提前到设计里，实际写到文件上

设计“增加 PNG 支持”时，就打开已有上传测试。在原任务里写清本次影响的文件、处置、理由和保留覆盖，不必为每条断言建立新台账。

一段可执行的教学任务可以是：

> 更新格式约定，JPEG 与 PNG 均支持，保留现有大小、内容校验及用户隔离。把原来的 PNG 拒绝用例替换为有效 PNG 正例；保留 JPEG 和受保护负例，增加伪装 PNG 的无效内容。核对页面文件选择限制和实际上传入口，读取保存后的图片。共享样本修改前检查其他消费者；若旧解码库同步退役，另列仍需处理的历史读取和退出条件。

这段话把新行为和旧测试接到了一起。接口已经明确，就在设计同一轮准备可执行用例；尚有争议，则记录具体缺口和最早能运行的位置，不用永久跳过的空测试冒充覆盖。

后续几个环节沿用同一个决定：实现核对新允许与旧保护；评审一起看生产代码、断言、样本和运行选集；验收检查删除是否落实、保留用例是否真的被收集并执行。不要每个环节再复制一套处置清单。

普通小修复也可以这样做，无需为了调整几条断言新建完整设计项目。改变接口、数据或权限时，仍按项目已有流程处理。

## 六、测试慢，先找能消掉的重复工作

慢测试不一定要删。也许只是同一批源码读了两遍、每个用例重复创建昂贵环境，或者为了等时间到期而真的等待。

这类优化可以先保留行为断言：复用同一轮已经读取的内容；合并真正重复的装配；用受控时间代替无意义等待。共享辅助函数应避免引入可变状态，否则减少几行代码可能换来相互污染。

时间控制还要作用在真正作判断的地方。应用内的模拟时钟不会自动改变数据库时钟；数据库用例应让数据库实际读到预先设置的到期事实。检查内容不能因为运行得更快而改变。

最后同步运行入口和活动选集。删掉最后一个用例后，运行配置还指向它，测试就没有真正退出。只把慢用例移出默认集合，通常也只是把成本推迟。

收益用可比运行观察，不拿少了几个文件当作节省时间的证明。

## 七、下一次遇到旧测试失败，先问它还在守什么

面对那条“PNG 应被拒绝”，现在可以作出有依据的处置：产品已经允许合法 PNG，所以替换旧格式限制；无效内容、大小和用户隔离继续保护；再沿页面上传到保存结果确认新路径。

相比前一篇[文档、代码和测试共同演进](docs-code-tests-evolve-together.md)，这里更进一步：每组旧测试还应该有明确去向，不能只管新增。

**让测试继续帮助研发，靠的是让它守住当前承诺，并在承诺变化时同步演进。** 过期要求不应逼实现退回去，有效保护也不能因为挡住绿灯就被删掉。
