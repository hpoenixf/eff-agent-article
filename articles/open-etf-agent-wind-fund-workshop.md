# 让 Agent 查基金：为什么不能只接一个行情接口？

「筛出几只同方向的 ETF，再看看它们最近的表现」是一句话，却不是一个数据请求。前半句要找候选，后半句才涉及具体基金和时间序列。如果工具只会查收盘价，Agent 即使拿到了真实数字，也回答不了基金如何入选、净值表现如何，更不能据此断言哪只更适合买。

Open ETF Agent 先从一个刻意窄的入口开始：指定代码和日期，只查场内日收盘。它足以回答一个清楚的问题，也让我们有一条独立于模型的取数路径。研究任务才需要在这条路径之外，引入不同数据工具，并把它们的口径带回报告。

## 先自己跑一次，只问一个明确的问题

在 [Open ETF Agent v0.38.0](https://github.com/hpoenixf/open-etf-agent/releases/tag/v0.38.0) 的代码目录，用文档要求的 Node.js 版本安装依赖。先看帮助；只有自己已获准访问 Wind，才在本地以安全方式向进程提供 `WIND_API_KEY` 并执行第二条查询。不要把密钥抄到命令、项目文件或日志里。

```bash
npm ci
npm run wind:fund -- --help
npm run wind:fund -- 588200.SH 2026-06-01 2026-06-05
```

这个例子查一只 ETF 在指定区间的**未复权场内收盘**。读输出时看三件事：日期是否在窗口内，数据口径是不是未复权收盘，以及返回值有没有独立带回基金代码。若身份字段为 `request-only`，表示请求指定了标的，不代表供应商结果额外确认过它。没有交易的日期不补零。具体边界见[固定版本的手动查询说明](https://github.com/hpoenixf/open-etf-agent/blob/v0.38.0/docs/wind-fund-mcp.zh-CN.md)。

这条命令不把 Wind 回包自动发给模型，也不写进研究历史。已知基金代码、只要核实一个事实时，我仍会选这条短路径；不必为了用 Agent 而让模型参与取数。

## 给研究流程多个工具，不给它一条万能查询

回到「先找基金，再比较表现」。可以把它拆成三步：**筛选范围 → 锁定标的 → 按问题选择数据口径**。教学上，先用基金筛选找候选，确定代码后查档案；若要对比场内交易走势，才查 K 线；若要比较基金份额净值表现，就必须使用净值或业绩口径，不能拿场内收盘代替。这是选择思路，不是一份已实跑的多工具投资建议。

为什么不把 Wind 目录原封不动交给模型？目录说明服务有什么，回答不了当前研究是否允许使用、有无账号权限、返回值能否进入报告。研究接入采用范围明确的只读基金工具：由项目显式启用，Worker 按需发现兼容工具；每次发送工具所需的结构化参数，而不是把整个提问或附件交给供应商。它允许多个工具组合，但不开放账户、交易或任意透传。代价是新接一种业务字段，需要单独核对输入约束和结果含义。对需要逐项说明来源的研究，这比让模型猜字段更可控。

## 报告可重开，不等于原始文件已取回

下面三种结果，界面上都可能表现为「没有表格可用」，报告里却应区分：

| 观察 | 应当怎样解释 |
| --- | --- |
| 查询成功，返回明确的空表 | 当前筛选条件未返回匹配，不代表市场上不存在相关基金。 |
| 无权限、超限或回包结构无法核对 | 本次没有取得可用数据；不是空表。 |
| 返回可核对的结构化记录 | 可以按供应商数据注明来源与口径；如果没有另行取得原始文件，不能附上假想的原文引用。 |

项目的多工具接入与上面的稳定命令是两条链路。在 **0.38.1 候选**的一次受控演练中，脚本替模型调用了基金筛选，实际取得 Wind 的结构化记录；随后保存的研究报告可以在另一次读取中打开。这验证了「研究流程能调用已启用的外部工具，输出也能保存并读回」，没有验证真实模型能自行制定上面那条路线，也没有把供应商记录伪装成编号原文引用。

接入下一个金融数据源时，我会沿这三层分别检查：**工具先独立取到正确口径，研究流程再验证确实消费它，最后用新进程读回报告并核查出处。** 第一层出问题，不急着改提示词；最后一层不成立，也不能靠生成一份看起来完整的文本补上。
