# Agent 开发与后台开发有什么不同：从一次请求到长期个人助手

如果已经做过后台应用，第一次接触 Agent 往往会觉得熟悉：接收请求、查资料、调用接口、保存结果，再返回给用户。把模型放在中间，似乎就是一个带自然语言入口的业务系统。

真正的变化出现在运行过程中：**下一步做什么，不再全部由开发者提前写好，而可能由模型根据刚刚看到的材料临时决定。** 这个决定还会受到上下文、工具描述、历史摘要和用户偏好的影响。

因此，Agent 工程是在成熟的后台工程基础上，接纳一个具有语义不确定性的决策环节。开发者既要让它能探索，也要让每次行动有范围、每次中断能解释、每份成果能取得。到了个人助手阶段，还要让这些约束跨越时间与用户的变化。

本文沿一个教学任务展开：先比较两份基金披露并生成报告，随后把需求扩展为“以后继续帮我关注，有重要变化再告诉我”。我们先看工具怎样改变控制权，再看长任务如何跨越中断和人的等待，最后讨论长期个人助手为何需要重新判断目标与条件。合成案例不代表真实投资研究或自动交易能力。

公开实现以 **2026 年 11 月 3 日核对的 Open ETF Agent v0.19.0** 为基线，主流体系采用同日查阅的官方资料。Open ETF Agent 是适合拆解机制的本地教学项目；Claude Agent SDK、Codex、OpenAI Agents SDK 和 LangGraph 则提供不同层次的运行能力。它们在本文中承担比较坐标，不构成产品排名。[版本与源码入口](https://github.com/hpoenixf/open-etf-agent/releases/tag/v0.19.0)

## 一、从同一个任务，看见控制方式的变化 {#一、从同一个任务-看见控制方式的变化}

假设用户说：“比较这两份基金材料，告诉我发生了什么变化，附上来源，保存一份报告。”

规则明确时，后台程序完全可以完成它：读取指定文件，校验日期和字段，执行固定计算，再套用报告模板。遇到缺字段就返回错误，遇到需要人工确认的情况就进入审批流程。这种方案容易测试，也便于复算。

但开放任务可能在读完材料后才暴露真正的问题：两份文件的统计时点不同，某个表格只披露部分项目，所谓“增长”使用了不同的分母。系统需要决定：补读原文、寻找可比口径、换一种分析方法，还是只给出有条件的结论。

这里才出现模型的价值：它可以根据观察提出新的研究动作。与此同时，模型也可能误判缺口、选择错误工具，或者在没有足够依据时写出流畅结论。

| 工程问题 | 规则驱动的业务路径 | 引入模型决策之后增加的责任 |
| --- | --- | --- |
| 下一步怎么选 | 代码、规则、工作流规定分支 | 校验模型临时提出的动作，并观察是否推动任务 |
| 输入怎样影响行为 | 字段及业务状态进入明确逻辑 | 自然语言资料、摘要和工具结果也会改变决策 |
| 状态要保存什么 | 业务对象、事务与流程进度 | 还要保存实际模型输入、原提案、原结果和未知效果 |
| 调用失败怎么办 | 按接口语义重试、补偿或转人工 | 先区分未派发、已完成与结果未知，再决定是否继续 |
| 如何判定完成 | 满足明确业务条件 | 同时检查执行事实、答案质量与用户实际取得的成果 |
| 如何控制成本 | 请求、资源、队列和配额 | 还要约束搜索、摘要、子任务和复核带来的累计开销 |

这些不是两个互斥世界。工作流引擎早已支持动态分支、异步和长期任务，Agent 也完全可以嵌在一条固定流程中。变化在于：**部分控制决策由模型产生，而模型的判断条件本身也在不断变化。**

## 二、最小 Agent 是一个观察循环，工程难点在循环之外和交接之中 {#二、最小-agent-是一个观察循环-工程难点在循环之外和交接之中}

一次模型请求可能返回答案，也可能返回工具调用提案。运行时接住提案，校验后调用工具，把真实结果放进下一次模型输入。新观察再次改变后续选择，直到交付、等待或停止。

Claude Agent SDK 已把 Claude Code 使用的循环、工具和上下文管理提供给应用；OpenAI Agents SDK 的 runner 也会围绕工具调用、交接和最终输出继续运行。这说明今天未必需要自己从零写一套循环，但仍须理解它把哪些责任交给了应用。[Claude SDK](https://code.claude.com/docs/en/agent-sdk/overview) · [OpenAI runner](https://developers.openai.com/api/docs/guides/agents/running-agents)

以 Open ETF Agent 为例，模型可以提议读取某页、执行计算或保存报告。工具宿主会检查工具范围、文档范围和参数，运行时记录实际派发及结果。模型说“已经保存”，和宿主留下可回读的文件回执，是两种不同的证据。[公开运行时与工具实现](https://github.com/hpoenixf/open-etf-agent/tree/fbefc074f161ae8de5b93060beae5b542de31038/src)

### 工具接口不仅供程序调用，也在教模型如何行动 {#工具接口不仅供程序调用-也在教模型如何行动}

普通接口的调用方通常按照既定契约编程。模型调用工具时，还会根据工具名称、参数说明和返回格式推断用途。一个叫 `query` 的万能工具，可能把资源范围、分页、时间口径和失败语义都留给模型猜。

更好的工具表面会让关键区别直接可见。例如“读取已授权文档的某一页”，就比“读取任意路径”更容易限定范围；返回文档版本、页码和完整性信息，也比只返回一段字符串更容易支持后续核查。

Open ETF Agent 的 `read_result` 回读已经取得的原始结果，而不是悄悄获取同一位置的最新内容；绑定来源的计算保留输入引用，CSV 可以继续消费同一个计算结果。这样，报告中的数字、附件中的数字和当时读到的依据才有机会对上。[工具合同](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/src/tools.mjs)

### Skill、MCP 与权限回答的是不同问题 {#skill、mcp-与权限回答的是不同问题}

Skill 适合封装一种可复用的方法：先查什么、如何比较、遇到缺口怎样处理，以及必要的模板和资源。MCP 提供外部工具与数据接入的协议。它们能改善 Agent 的工作方式，却不自动证明某个动作已经获得当前用户的授权。

这里也不能把某一项目的规则说成所有平台的共同规定。Open ETF Agent 中，Skill 不自行扩大原授权；Claude SDK 则允许宿主根据受信项目或个人 Skill 的 `allowed-tools` 配置预批准工具，并受组织设置约束。决定权限的是宿主接受的可信配置和策略，外部资料正文不能凭一句指令取得相同地位。[Claude Skill 机制](https://code.claude.com/docs/en/agent-sdk/skills)

Codex 对另一组区别的表达很直观：沙箱限定执行时可接触的文件、网络等资源，审批策略决定什么时候需要进一步批准。审批通过与执行隔离各有作用，不能用更聪明的模型替代其中任何一项。[Codex 执行边界](https://learn.chatgpt.com/docs/agent-approvals-security)

## 三、开发者要管理两类状态：系统发生了什么，模型现在看到了什么 {#三、开发者要管理两类状态-系统发生了什么-模型现在看到了什么}

后台工程师习惯把数据库当作事实来源。Agent 还多出一份有限的“工作视图”：这次模型请求真正收到的上下文。

某份资料已经存入数据库，不代表模型已经读到它；模型读过某个片段，也不代表之后每一轮都还能看到；摘要中写着“已经验证”，更不能代替原始验证结果。

理解这一区别，可以先分清四种信息，而不急着创建四套服务：

| 信息 | 在任务中的作用 | 不能替代什么 |
| --- | --- | --- |
| 原始证据 | 当时读取的文档、页面、版本与计算依据 | 模型生成的归纳不能反过来充当原文 |
| 执行事实 | 提案、派发、回执、剩余额度与终态 | 聊天摘要不能决定某个操作是否已经发生 |
| 当前上下文 | 本轮模型需要的目标、材料、进展和未解问题 | 它容量有限，不是全部历史的唯一副本 |
| 跨任务记忆 | 以后仍有价值的偏好、事实与经验 | 它不能代替当前指令或操作授权 |

上下文工程由此变得具体：不是把能找到的材料都塞进去，而是选择对当前判断有用、仍然有效、来源清楚的内容。需要时能回读原文，不需要时可以省略。

这也解释了为什么“把上下文窗口做大”不是唯一答案。更大的窗口可以保留更多材料，却不会自动解决内容之间的冲突、旧偏好失效、工具结果诱导或重复研究。选择什么进入下一次请求，本身就是应用行为的一部分。

LangGraph 将线程内的 checkpoint 与跨线程 store 分开；Claude SDK 也明确区分会话历史和文件系统状态，会话恢复或分叉不会自动复制、回滚文件。不同体系的实现不同，但共同提醒我们：**恢复对话、恢复计算位置和恢复外部工作成果，不能混用同一个“恢复成功”。** [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence) · [Claude 会话](https://code.claude.com/docs/en/agent-sdk/sessions)

<span id="五、v0-19-的一个真实教训-辅助模型的工作-也会成为失控来源"></span>

上下文管理还会改变资源分配。摘要、专家核查和补充检索都是实际工作，应计入同一项任务的预算，而不只是限制主对话轮数。Open ETF Agent 曾出现报告已保存、主任务未结束却重复摘要同一批材料的情况；它的修复转向校验并复用仍有效的摘要范围，而不是单纯放大调用额度。这个例子提示：维护上下文的机制也要有停止条件。教学实现主要约束调用额度，不等于完整的 token 或费用账本。[设计来路](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/openspec/changes/v019-module-composition/design.md)

## 四、任务越长，越要承认“我还不知道发生了什么” {#四、任务越长-越要承认-我还不知道发生了什么}

用一个普通后台开发也熟悉的例子：某个获准操作已经发往外部系统，对方可能已经完成，本地却因为断网没有收到回执。

如果它只是查询，重新读取也许可以接受，但新结果仍可能对应另一时点。如果它是发邮件、建订单或修改日历，重新执行就可能制造第二份效果。模型重新“想一遍”解决不了这一信息缺口。

关键分界在派发之前与之后。派发前明确被拒绝，可以在条件允许时修正参数或重试；派发后有可靠结果，就按原结果继续；派发后没有可靠结果，应保留未知，而不是把本地超时翻译成远端失败。

Open ETF Agent 从持久恢复设计开始，就把原 Run 的提案、工具派发、结果提交和结果消费分别记录。完整提案已经保存时，可以继续消费原提案；工具已经派发而结果未知时，不能重新执行来假装恢复。只有明确支持核对的适配器，才可以查询原操作是否完成。原授权、预算和截止时间也不会随着重启刷新。[恢复设计](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/openspec/changes/v07-trusted-recovery/design.md) · [运行时恢复分支](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/src/runtime.mjs)

这不是通用的外部“恰好执行一次”保证。数据库状态与外部动作通常不在同一个事务里，还需要业务幂等键、结果查询或明确的人工核对路径。LangGraph 官方也提醒：恢复 `interrupt()` 所在节点时可能重新运行代码，即使副作用放在审批之后，写入已成功、节点尚未完成时的故障仍可能导致重复写入。[LangGraph 中断与副作用](https://docs.langchain.com/oss/python/langgraph/interrupts)

持久恢复还会把视野推向人机协作。假如两份材料的统计口径无法直接比较，Agent 可以说明差异，请用户选择比较范围；这不是执行失败，也不必让模型反复猜测。系统应保存具体问题和当时的候选，等待回复，再核对回复是否仍对应当前任务与有效条件。保存 checkpoint 解决了“别丢进度”，却没有替用户作决定；能继续运行，也不代表现在应该继续。

对 Agent 来说，这类问题格外容易被“自主重试”的直觉遮住。一个好的运行时有时应该阻止模型继续行动：它需要先把原操作核对清楚，而不是给模型另一次机会猜测。

## 五、完成有三个层面，Agent 测试也需要三种观察 {#六、完成有三个层面-agent-测试也需要三种观察}

对开头的报告任务，至少有三个不同问题：流程是否正确结束，结论是否站得住，用户是否拿到了可读的成果。

工具成功读取文件，只说明文件读到了；保存报告成功，只说明某些字节保存了；报告引用了真实页面，也不能自动证明每句话都由该页面支持。Open ETF Agent 的运行结果保留 `semanticStatus: unreviewed`，就是把执行完成与语义评审分开。[结果与回读说明](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/README.zh-CN.md)

因此，传统测试仍然有明确位置：权限、参数、计算、事务、恢复和产物完整性，需要确定性的断言。模型引入的新问题，则要用任务样本检查它有没有找对依据、识别不可比条件、解释不确定性，并在证据不足时适当停止。

最后还要回到用户侧：报告能不能打开，附件与正文是否一致，中途失败后已经保存的阶段成果能否继续阅读。一个界面显示“已完成”，却下载不到文件，依然没有完成交付。

对研究任务，评测不宜机械要求唯一工具顺序。只要许可和业务约束相同，模型可能用不同路径找到相同依据。反过来，轨迹非常漂亮、工具调用很多，也可能没有解决原问题。应把目标完成、依据质量、执行可靠性和成本放在一起观察，避免只优化其中最容易计数的一项。

## 六、主流 Agent 给出的共同启发：复用运行能力，保留业务责任 {#七、主流-agent-给出的共同启发-复用运行能力-保留业务责任}

成熟框架已经不只提供“模型调用加一个循环”。会话、工具执行、人工审批、上下文管理、持久恢复和轨迹观测，都有现成的实现。它们真正的区别，是**把什么作为执行单元、由谁决定下一步，以及应用怎样接入自己的业务约束**。下面仍用“两份材料比较并保存报告”作教学对照，不把官方能力列表当作本文跑过的测评。

### Claude Agent SDK：把工作环境交给一个可执行的助手

Claude Agent SDK 复用 Claude Code 的工具、循环和上下文管理。相比自己拼接每轮消息、解析工具调用再继续，它更接近把一个具备读写文件、运行命令和调用扩展工具能力的执行器嵌入应用。上下文接近上限时，框架会压缩历史；这减少了应用维护循环的工作，但早期细节可能丢失，关键业务约束不宜只放在很早的一轮对话里。[运行循环](https://code.claude.com/docs/en/agent-sdk/agent-loop)

在比较材料的场景里，应用可以准备独立工作目录，让 Agent 阅读两份文件、按需运行受控计算并生成报告。若有一项核对需要独立上下文，可以交给专门子 Agent，主任务再整合结果。这里的收益不是“角色越多越聪明”，而是把长材料和专门方法从主上下文中分离；简单并行读文件仍可用普通并发完成。[子 Agent](https://code.claude.com/docs/en/agent-sdk/subagents)

真正需要认真设计的是执行环境。`allowedTools` 表示自动批准规则，不是“除此之外绝对没有工具”；部分调用在前置规则批准后不会进入 `canUseTool`。若租户范围检查必须逐次执行，应选择覆盖该调用路径的检查点，例如 `PreToolUse` hook，并由工具后端再次校验业务身份。权限规则也不等于文件系统和网络隔离。[权限](https://code.claude.com/docs/en/agent-sdk/permissions) · [Hooks](https://code.claude.com/docs/en/agent-sdk/hooks) · [安全部署](https://code.claude.com/docs/en/agent-sdk/secure-deployment)

它适合需要 Agent 在工作环境中持续操作的任务，但 `resume` 或 `fork` 不能替代工作区管理：分叉会话历史不会复制或回滚文件系统。要让两个候选报告互不覆盖，应用仍要准备各自的工作区或版本化产物。[会话](https://code.claude.com/docs/en/agent-sdk/sessions)

### OpenAI Agents SDK：把模型协作接入应用自己的调用链

OpenAI Agents SDK 提供运行循环、函数工具、交接、会话、审批和 tracing。已有后台服务可以把“读取授权资料”“计算可比指标”“保存报告”包装为工具；函数签名与说明形成模型可见的参数契约，业务服务继续掌握数据访问和写入规则。框架负责接住模型提案并推进循环，不要求业务数据库让位给聊天记录。[工具](https://openai.github.io/openai-agents-python/tools/)

协作有两种不同结构。把专家作为工具调用，主 Agent 保持控制，接收专家结果后继续比较与成稿；handoff 则把对话控制交给接收方。前者适合“请专家核查统计口径，再由我完成报告”，后者适合“这个请求现在由另一类服务负责”。交接还涉及历史范围：默认传递的会话未必适合所有专家，应明确筛选输入，不能把压缩历史误当作脱敏。[交接](https://openai.github.io/openai-agents-python/handoffs/)

状态支持也比“自己保存所有消息”更完整。Session 可自动加载和保存会话历史；需要人工批准的运行可以暂停为可序列化的 `RunState`，由应用存储后再恢复。两者分别解决会话历史与可恢复执行状态，不能混为一种业务事务。比如报告允许自动保存，但发送给外部收件人要审批：审批应绑定具体收件人、报告版本和动作，服务端核验批准者并防止旧批准重放。反序列化一个状态对象本身不会完成这些认证。[Sessions](https://openai.github.io/openai-agents-python/sessions/) · [人工审批](https://openai.github.io/openai-agents-python/human_in_the_loop/)

若等待需要跨越进程重启或很长时间，SDK 也提供与 Temporal 等持久工作流系统集成的路径。应区分三层：Session 保存会话，`RunState` 保存可继续的运行状态，持久编排基础设施负责长期执行与唤醒。不能因此把 OpenAI SDK 归为“只有内存循环”，也不能把序列化状态误认为已经部署了可靠的后台执行服务。[长任务与持久执行](https://openai.github.io/openai-agents-python/running_agents/)

Guardrails 与 tracing 让检查和排障更容易，但覆盖范围必须读清。默认并行的输入检查可能与 Agent 执行重叠；若要求检查通过之前绝不能调用工具，就应采用阻塞检查。输入 guardrail 也不是每次工具调用的检查；逐次动作仍需对应工具管线或后端校验。轨迹能显示模型、工具和交接，却不能代替租户权限，也不自动证明结论正确；其中的输入输出还可能包含敏感材料，需要决定保留什么。[Guardrails](https://openai.github.io/openai-agents-python/guardrails/) · [Tracing](https://openai.github.io/openai-agents-python/tracing/)

### LangGraph：把不确定的判断放进可恢复的流程

LangGraph 以图状态、节点和持久化组织工作，既能表达预定工作流，也能容纳模型动态选择工具。材料比较可以拆成读取、口径检查、必要时询问用户、计算、成稿几个阶段；只有真正需要语义判断的部分交给模型，确定性计算仍是普通代码节点。图的价值不是强迫所有任务走同一条线，而是让应用明确哪些转移可以自主决定、哪些必须停下来。[工作流与 Agent](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

Checkpointer 保存线程内执行状态，store 承载跨线程数据。持久化也有取舍：同步写入与异步写入的故障窗口不同，不能看到“有 checkpoint”就推断每一步都已安全落盘。对重要审批和外部写入，应按实际恢复要求选择持久化方式。[持久化模式](https://docs.langchain.com/oss/python/langgraph/checkpointers)

`interrupt()` 可以暂停并等待输入，再以原线程身份恢复，但恢复会重新执行所在节点开头的代码，不是从暂停的那一行继续。假设报告发送成功后、节点提交前进程崩溃，恢复仍可能再次走到发送步骤。把发送放在审批之后并不足够，目标接口还需要稳定幂等键或原结果查询。查询暂时没有结果也不代表未执行；仍无法确认时应保留未知，不能自动重做。框架解决“从哪一段工作继续”，业务接口解决“这个效果是否已经发生”。[中断与副作用](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 同样叫 Agent，交给框架的责任并不相同

| 任务中的需要 | 可以复用的框架能力 | 应用仍要作出的判断 |
| --- | --- | --- |
| 在文件与工具环境中完成工作 | Claude SDK 的循环、上下文、权限与子 Agent | 工作区隔离、资料范围、产物版本和真实业务身份 |
| 让现有服务参加模型决策 | OpenAI Agents SDK 的工具、协作、Session、审批与轨迹 | 审批对象、业务幂等、敏感信息和结果验收 |
| 让动态研究嵌入长期流程 | LangGraph 的状态、检查点、条件路径与中断 | 哪些节点可重做、如何处理未知效果与状态迁移 |

Codex 同样说明执行边界与审批策略需要分别理解：允许运行一条命令，不意味着它可以访问所有文件和网络；命令运行成功，也不等于改动符合产品需求。工作区、验证与发布仍有独立的条件。[Codex 安全边界](https://learn.chatgpt.com/docs/agent-approvals-security)

这些能力有重叠，上表是比较视角，不是排他分类。Open ETF Agent 则继续充当可拆解的教学样本：原始证据、共享预算、未知结果与有限组合可以沿固定源码检查，但不能凭教学样本的约束推断成熟框架也缺少对应能力。真正值得比较的是：同一份资料、同一次审批、同一个外部效果，在选定框架里分别由谁保存和验证。

## 七、从任务型 Agent 到个人助手，变化发生在“以后”两个字里 {#八、从任务型-agent-到个人助手-变化发生在-以后-两个字里}

到这里，系统能够围绕一次任务探索，保存执行状态，并在需要时停下来等人。但它还没有回答：**这一份报告交付以后，为什么还要再工作，下一次沿用什么、重新确认什么？**

现在用户说：“以后每周五帮我看这两份材料有没有更新。有重要变化再告诉我，报告短一点，保留来源。”这建立的是持续委托，不是把原来的模型循环延长。个人 Agent 的连续性来自长期目标、当前有效的个人信息和获准行动，而不只是聊天记录。

长期委托应能被查看和修改：“每周五”是触发条件，“这两份材料”限定资料范围，“报告短一点”是呈现偏好，“有重要变化再通知”是交付条件。偏好不能授予发消息的权限，定时器也不能替用户决定什么变化值得关注。把这些区别保留下来，才知道用户改变主意时究竟要调整哪一部分。以后更换通知渠道或扩大资料范围，也应作为委托变化处理，不能从旧偏好自行推导。

### 长期目标可以持续，单次执行仍应有边界 {#长期目标可以持续-单次执行仍应有边界}

这种视野扩展也带来新的代价。一次请求的调用者通常还在线，长期委托的用户却可能已经改变计划；触发发生时，需要核对目标是否仍有效，而不只是从数据库取出旧提示词。正在等待人的决定，也不能被另一次定时触发悄悄绕过。

一个目标可能持续数月，一次执行只处理本轮资料和条件，单次模型请求则只处理当前上下文。等待新披露或用户补充时可以释放计算；持久的是委托和继续工作的依据，而不是一段永不停止的思考。

Open ETF Agent 的 Worker、回复和 Schedule 提供部分积木：确认后显式唤醒原任务，或保存问题后等待回答。但 v0.19 没有后台常驻调度服务，Response 与 Schedule 也没有任意组合的联合等待协议。到点执行与等人回复分别可用，不自动得到一条可取消、可过期、可恢复的完整长期流程。[组合支持边界](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/docs/composition.zh-CN.md)

## 八、个性化的难点，是用户改变主意以后系统能不能跟上 {#九、个性化的难点-是用户改变主意以后系统能不能跟上}

从一次任务走向长期委托，另一项变化是：用户信息也会过期。用户通常只看摘要，不代表这次不需要完整推导；曾经关注一个项目，不代表它值得永久跟踪。稳定偏好提供默认值，当前指令可以覆盖默认值，阶段状态应有适用范围；授权仍须从可信入口取得。

### 记忆需要来源、范围和可纠正性 {#记忆需要来源、范围和可纠正性}

重要记忆应能解释来自用户明确陈述、一次观察，还是模型推断，何时更新、在哪些任务里有效。一次点击不能直接升级为长期偏好，反复引用也不能把推断变成用户原话。用户需要能够查看、更正或暂时不用它。

### 遗忘是一条后续消费链，不能只看数据库里少了一行 {#遗忘是一条后续消费链-不能只看数据库里少了一行}

如果用户把某个项目的“简短报告”改为“保留完整推导”，旧偏好可能仍藏在历史工具结果或工作摘要中。只更新检索库，没有处理这些后续输入，系统仍可能表现得像没有听见更正。

Open ETF Agent 使用带类型的 Memory 身份与版本，在构造后续模型输入时过滤失效内容，并使依赖旧记忆的工作笔记失效。这里保护的是已知的消费路径；已经发给模型的字节无法撤回，旧报告也仍是历史产物，不能声称任意自然语言中的残留都已消除。[Memory 投影](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/src/memory-projection.mjs) · [实际输入验证](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/test/memory-consumer.test.mjs)

记忆还有范围成本：一个项目中允许使用的信息，不应默认进入另一个项目或专家的上下文。应用需要在“更了解用户”与“只带入完成当前任务所需信息”之间作选择。保留更多历史既可能提高连续性，也可能让无关资料、过时推断与敏感信息继续影响后续工作。

检索回答“找到什么过去”，个性化还要回答“这段过去今天是否适用”。这是跨时间服务比单次请求多出的责任，不是换一个更大的向量库就能解决。

## 九、主动性要服务用户的进展，也要保护用户的注意力 {#十、主动性要服务用户的进展-也要保护用户的注意力}

能在用户离开后继续工作，不意味着每次运行都应发送通知。对材料比较任务，资料未更新时重复生成报告没有意义；变化很小却立即推送，也可能只是增加打扰。主动性要分别判断：有没有新事实，是否影响当前目标，是否值得现在让用户阅读。

获准事件唤醒后，先核对资料版本、目标与适用条件；没有变化就继续等待。有变化再组织必要上下文，研究其影响，并按约定的重要性条件交付。等待来源、等待用户决定和核对未知效果，是不同的停顿，不应统一显示为“正在思考”。

用户说“这个项目先停掉”时，尚未派发的工作应停止按旧目标推进；已经发生的效果与未知回执则继续如实保留。产品评价也应回到用户：是否少重复交代，纠正是否生效，重要变化是否及时交付，无效打扰是否减少。调用次数本身回答不了这些问题。

## 十、未来的工程重心，会从运行一个模型扩展到维护一段委托 {#十一、未来的工程重心-会从运行一个模型扩展到维护一段委托}

这是基于前述机制的展望，不是 v0.19 已完成的产品清单。个人助手可能让用户围绕同一个目标，持续看到新证据、结论变化和待决事项，而不必在多个应用之间反复搬运上下文。界面因此不仅展示回答，还要让人理解当前委托、等待原因与下一次触发，并能修改或结束它。

### 通用运行能力会更容易复用，领域责任仍需要有人承担 {#通用运行能力会更容易复用-领域责任仍需要有人承担}

前面的框架实践已经展示了这种分工：循环、会话、检查点和工具调度可以复用，资料资格、计算口径、重要性判断与外部效果仍需具体产品负责。越容易搭起一个会行动的 Agent，越需要明确它在什么条件下不该继续行动。

### 模型与工具会升级，旧委托却不能被随意改写 {#模型与工具会升级-旧委托却不能被随意改写}

长期目标可能比一版模型或接口活得更久。升级后，原任务的范围、原始材料与已发生的效果仍然存在。Open ETF Agent 的版本化运行定义和旧读取器拒绝规则提供了一个具体提醒：读取旧成果与继续旧执行的兼容条件不同，保存一个摘要或 hash 也不能重建原 PDF 字节与页面。[升级说明](https://github.com/hpoenixf/open-etf-agent/blob/fbefc074f161ae8de5b93060beae5b542de31038/docs/upgrade-guide.zh-CN.md)

例如，新模型更善于搜索，并不自动允许原本只读两份文件的任务访问互联网；新版工具支持发送通知，也不代表旧委托已批准这个新动作。版本升级改变的是可用能力，当前委托决定的仍是本次可以使用哪些能力。

产品可能需要让旧任务结束后切换，或进行明确的迁移；迁移改变了范围，就重新取得适用授权。更成熟的个人助手，不是默默扩张一份画像和权限，而是让用户理解它为什么继续、为什么等待，以及怎样收回委托。

## 回顾：我们的视野是怎样逐步展开的

最初我们面对一次请求，关心输入是否有效、业务规则是否执行、结果是否返回。开放任务让这个视野扩大：资料可能暴露新问题，系统需要根据观察决定下一步，于是工具不再只是固定调用链的一环，也成为模型探索的接口。

再往前，任务可能跨越进程和人的等待。此时要维护的已经不只是一次响应，还包括原证据、已发生的效果和继续工作的条件。到了长期个人助手，同一个目标会产生多次执行，用户也会改变主意；每次唤醒都需要重新判断什么仍然有效，何时应该工作，何时应该安静。

**视野扩大，不意味着旧工程被替代，而是我们承诺负责的时间和判断范围变大了。** 数据库、事务、幂等、隔离和可观测继续支撑系统；成熟框架把其中许多运行能力变得可复用。开发者新增的工作，是把模型的探索接进这些可靠机制，让一次正确行动最终成为一段有分寸、可解释、可收回的长期委托。
