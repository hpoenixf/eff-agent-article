# 聊天记录、上下文、记忆、检查点，Agent 怎样接上过去？

<LearningPathNav />

昨天你让助手比较两版产品指南，已经读完 A。今天打开程序，说一句“继续”。助手应该重新读 A，接着读 B，还是直接打开昨天的报告？

只看这两个字，很难知道。需要先确定用户想接上什么，以及系统实际保存了什么。聊天记录、上下文、记忆和检查点，都与过去有关，却分别回答不同问题。

下面仍用 Atlas Notes 合成文档比较来解释。用户要求比较两版导出能力，并明确保存报告。我们把一次任务分成“读取 A、读取 B、比较、保存”几个便于理解的动作。实际 Agent 可以根据观察选择不同路径。

## 四种“留下来”，对应四种需要

| 用户的需要 | 主要依靠什么 | 能从中找到什么 |
| --- | --- | --- |
| 回看昨天说过的话 | 聊天记录 | 原问题、补充要求与历史回答 |
| 让这一次模型接着判断 | 上下文 | 本轮挑选的要求、资料和最新观察 |
| 下次研究继续参考表达偏好 | 长期记忆 | 被保存且仍适用的跨任务信息 |
| 进程退出后接着执行 | 检查点及执行记录 | 原任务状态、已完成动作与接续位置 |

一份实现可以把它们存放在同一个数据库中，甚至共享部分数据。理解它们时，更重要的是看使用目的、更新时机和能支持的动作。

## 聊天记录怎样变成本轮上下文

用户在页面上看见昨天的完整对话，会自然地认为模型也看见了。但页面读取历史和下一次模型请求，是两条需要接通的路径。

应用可能只把最近几轮放进输入，也可能选择摘要，或者让模型按需回读旧内容。这样可以控制容量和成本，但也产生一个排查问题。“昨天已经说过”的要求，究竟保存在历史里，还是已经进入这次实际请求？

假设昨天用户补充了“只比较免费版”。若今天输入只有助手写的简短结论，模型可能无法恢复这项限制。保留用户原文的读取入口，再把相关修正装进本轮输入，能够减少这种失真。

聊天记录还保存了当时的判断。旧回答中的“当前版本支持 CSV”带着当时条件。新问题涉及 B 版时，模型需要核对原文与版本，才能决定旧判断是否适用。

## 长期记忆为什么还要单独存在

有些信息需要跨越许多任务，例如用户明确保存的“先给比较表”。如果每次都从整段聊天中寻找，既费资源，也容易把一次临时要求误当成长期偏好。

长期记忆允许系统挑出适合积累的信息，保存范围与来源，并支持更正和遗忘。下次使用时，先取得相关且有效的记录，再决定是否加入当前输入。

于是，模型的一次请求里可以同时出现聊天历史与记忆。前者帮助理解刚才谈到哪里，后者提供经过选择的跨任务背景。当前用户提出新要求时，也需要在输入中明确呈现，让模型处理适用关系。

产品指南是另一个对象。它描述产品事实，应保留原始版本与可回读位置。可以把记忆和文档都交给检索，但仍要区分个人偏好、原文事实与模型派生的结论。

## 继续执行为什么需要额外的事实

现在把问题换成进程退出。A 已经读取完成，程序准备读取 B。若想从这里接上工作，需要知道的内容比聊天文字更多。

```text
原任务及其身份
当前执行位置
已取得的 A 版结果与引用
已消费和仍可用的资源额度
待处理动作及实际执行结果
已保存的报告与回执
```

检查点把受支持位置上的必要工作状态保存下来。执行记录、工具回执与产物存储则保留动作的实际结果。不同系统对这些对象的划分可能不同，检查点也可以引用外部记录。

恢复时，系统要从这些记录重建下一步所需状态。能够在哪个位置恢复、怎样处理进行中的工具调用，取决于实现提供的契约。仅保存消息列表，通常无法回答一项外部写入到底有没有发生。

## 同一句“继续”，先看中断发生在哪里

**情况一，A 的读取已经完成并保存。** 可以核对原结果，在受支持位置继续取得 B。重新读取是否合适，还取决于任务需要原快照还是最新资料。

**情况二，保存报告已经发出，但确认信息丢失。** 文件可能已经写入。此时先核对原操作记录、产物与回执，再决定后续动作。直接重跑可能重复产生效果。

**情况三，报告早已完成，用户只是回来阅读。** 打开已保存的版本就足够。需要另外研究新问题时，再建立相应任务。

这三种情况分别涉及接续执行、核对未知效果和读取既有成果。一个统一的“继续”按钮也应在内部保留这些差异。

检查点本身不能提供新的权限与额度。沿原任务恢复时，需要使用原身份及其记录。新任务则按照新任务的入口准入。这里增加的持久化与一致性成本，适合有跨进程接续需求的工作。短小、可安全从头执行的计算，可以采用更简单的方式。

## 压缩以后，哪些东西还应找得到

长任务可能需要把早期材料整理成便笺，再从当前输入中移出大块原文。此时摘要帮助下一步判断，原始资料承担回查依据，检查点承担接续状态。

如果便笺记着“B 的导出条件待核对”，下一步可以回读原页。如果记录表明报告已经保存，模型的摘要也不能把这项效果改成未发生。

**压缩改变工作表示，持久记录保留对应事实。** 区分这两类用途，才能同时获得紧凑输入与可回查的研究过程。[我们的上下文压缩专文](./agent-main-run-context-compaction.md)

## 在 Open ETF Agent 中分别观察

本文以已发布的 **v0.26.0** 为固定版本。按[输入与知识篇的安装步骤](./prompt-context-rag-memory.md#在-open-etf-agent-中观察一次)准备项目后，可以先运行两个独立的离线示例。

```bash
npm run demo -- --case compact-and-reread
npm run demo -- --case explicit-memory --memory-library runs/concept-memory-library
```

第一个展示派生便笺与原文回读，第二个在一份专用合成记忆库中依次演示保存、更正与遗忘。记忆示例应选择新的空目录，查看 CLI 返回的保存、更正与遗忘回执。示例使用预设动作模拟模型选择。

进一步查看公开的跨进程接续测试，可以观察实际中断与接续位置的断言。它通过原运行系统验证受支持的恢复行为，仍属于离线机制检查。[跨进程接续测试](https://github.com/hpoenixf/open-etf-agent/blob/bcc12995c83abfbd5b37b9792f5a86ab74aa788e/test/durable-runtime.test.mjs)

```bash
node --test --test-concurrency=1 test/durable-runtime.test.mjs
```

下一次设计“记住我”或“继续”时，先把承诺说具体。用户需要回看交流、携带偏好、重新取得材料，还是接着原执行位置工作？选定需要，才知道该保存哪些信息，以及怎样检验它真的生效。
