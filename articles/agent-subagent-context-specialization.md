# Subagent 全景：独立上下文、专业协作与真实成果交接

![Subagent 全景：独立探索，共同完成一项研究](../visuals/panorama-subagents/cover.svg)

**只有当一段局部研究值得独立深入、成果能够被 Main 真正消费时，Subagent 才可能比 Main 直接调用工具更有价值。** 它的首要作用不是多开几个模型，也不是按 Web、PDF、Python 格式排流水线，而是隔离搜索与调试过程，同时把影响最终判断的原始依据交回来。

ETF Agent 最初给 Child 独立上下文，是为了让 Main 不必背着每一次 PDF 定位和 Python 修错。实际开发却发现另一个更难的问题：**过程隔开容易，成果、来源和责任不丢才难。** 一次 Child 有效交回引用但 Main 反复轮询、重新委派，最终仍未交付；另一次 Child 在独立工作区修正计算和 HTML 错误后交出可下载报告，Main 才真正接到了成果。

本文沿一次委派的完整生命周期展开：决定是否拆分，交出必要输入，让 Child 自主探索，接回成果与缺口，再由 Main 综合和交付。工具、方法、权限、预算与恢复分别回到原有责任方。先理解这一条链，再增加不同专家或有界对话，才能知道协作究竟在哪里产生价值。

## 一、先隔离过程，而不是把 Agent 的能力切碎

设想一个简化的投研问题：用户想比较某只 ETF 与现有组合的关系，需要核对产品材料，再计算持仓重叠或历史表现。

主 Agent 应该持续关注的是用户目标、比较口径、已有结论和未解决问题。但完成某个局部计算，可能要检查数据字段、修复代码、重新执行；阅读一份 PDF，也可能要多次定位章节、查看表格和核对脚注。

这些过程对当下的工作很重要，却不一定需要进入主 Agent 后面的每一次请求。

计算完成以后，Main 需要知道采用了什么数据、怎样计算、结果与限制是什么，不必继续背着几版错误脚本。条款已经核对以后，它需要保留原文依据和适用条件，不必反复携带所有文档搜索记录。

这就是这里所说的“上下文污染”：**局部试错和全局研究混在一起，已经完成使命的过程信息，继续占据后续思考的空间。**

这种动机与 Anthropic 在[《Effective context engineering for AI agents》](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)中介绍的子代理模式相近：让局部执行者在独立上下文中深入工作，再返回提炼后的结果，主代理负责综合。值得借鉴的是这种信息分工，而不是直接借用别人的性能结论。

不过，“独立上下文”不应该被实现为“能力残缺的小工具”。Web 子代理找到相关 PDF，应当能在许可范围内继续读；PDF 子代理遇到需要核实的网页，也不必机械地退回 Main。我们当前的专业配置明确保留了这种跨工具工作的空间。

**我们隔离的是工作过程，不是解决问题的能力。**

## 二、一个通用执行底座，配上不同专长

因此，我们没有为 Web、PDF、Python 分别开发三套 Agent。

核心结构是：**一套通用的子代理运行时，加上不同的专业配置（Profile），每次委派产生独立执行体。** 专业配置提供工作方法；实际工具和资料访问范围由宿主决定；父子执行继续受同一个根任务的资源约束。

### 图 1：共享执行机制，不共享一团上下文

![通用 Child 与 Main 的工具、方法、授权和成果关系](../visuals/panorama-subagents/architecture.svg)

图中的 Child 是每次创建的独立执行体。它复用共同运行机制，采用本次专业方法，在实际获准的工具范围内工作；Main 与 Child 继续共享原任务的预算、授权和生命周期约束，各自保留工作上下文。

Main 仍然保留直接调用工具的路径。它可以自己解决简单问题，也可以委派复杂局部工作；子代理交回成果，Main 再综合成用户需要的回答。

这与 [OpenAI Agents SDK 的 manager／agents-as-tools 模式](https://openai.github.io/openai-agents-python/multi_agent/)在职责上相近：主代理调用其他代理处理子任务，但继续拥有用户对话与最终回答。它不同于把对话控制权直接交给另一个代理的 handoff 模式。本文说的“成果交接”，不意味着转移用户对话。

“能力完整”也不是要求每个 Child 都拿到所有工具、所有数据和所有控制权限。我们的意思是，它能在获准范围内自主完成多步工作，而不是只能执行一个预设动作。最终发布和继续创建子代理等控制能力，仍有明确边界。

[Claude Code 的子代理文档](https://code.claude.com/docs/en/sub-agents)也体现了类似的区分：通用子代理可以处理需要探索与行动的复杂任务，同时存在只读等受限配置。**独立上下文、专业方法和工具权限是不同的设计维度，不必绑定成一件事。**

## 三、Web、PDF、Python、Reviewer，到底有什么不同？

我们的差异主要放在工作方法和关注重点上，而不是按文件格式划出不可跨越的边界。

| 方向 | 更关注什么 | 金融场景中的典型任务 |
| --- | --- | --- |
| **Web Explorer** | 来源选择、公开信息变化、交叉核验 | 核对基金公告、发行人披露及相关更新 |
| **PDF Reader** | 章节、表格、脚注、页码与阅读覆盖 | 检查产品条款、费用定义和风险披露 |
| **Python Analyst** | 输入口径、计算、错误修复和产物 | 计算收益回撤、持仓重叠，生成附表 |
| **Research Reviewer** | 遗漏、冲突、反例和脆弱假设 | 检查结论依据、是否还需要补查 |
| **投资研究视角** | 从不同投资方法挑战同一组事实与假设 | 用资产配置、尾部风险与风险分散视角复查同一项决策 |
| **Remind，非子代理** | 已发生的资源与执行事实 | 提醒剩余预算、时间与复盘时机 |

Web、PDF、Python、Reviewer 和投资研究视角都复用子代理执行机制，Remind 则是配套的运行时提醒。专业配置与投资方法本身不会授予额外工具或资料权限。

### Web 与 PDF：专长不同，但不按材料格式反复转派

Web 更重视“应该去哪找，以及不同来源是否一致”；PDF 更重视“这份材料实际写了什么，哪些部分真正读到了”。

例如，一段费用核查从发行人网页开始，最后落到 PDF 脚注，这仍然可以是同一个子代理的完整任务。我们没有要求它先把 PDF 地址交回 Main，再启动另一个 Child。反方向的网页核查也一样，相关交叉读取路径已有受控工程验证。

专业化的作用，是让执行者采用更合适的方法，不是制造更多交接。

### Python：接手一段计算工作，而不是接手一次函数调用

Python 子代理不只是运行代码。它需要理解计算目标，检查实际输入，处理报错，再解释结果与限制。

我们给这类配置的指导会强调日期对齐、单位、缺失值和输入来源，也明确区分“脚本执行成功”与“计算口径正确”。没有真实执行能力时，应当说明未执行，不能根据角色名称编造一个计算结果。

这种多轮局部工作，才是值得从 Main 上下文中隔离出去的部分。一次稳定的简单计算，Main 直接调用工具就够了。

### Reviewer：独立复核，不是最终审批

Reviewer 更像擅长 Review 的工程师。它可以检查原始依据、寻找重要反例，并在有价值时使用获准工具补查，而不是只能点评 Main 的摘要。

但它不能因为给出一个判断，就直接改写研究事实、要求 Main 必须采纳，或者阻断最终回答。独立执行与建议交接已经有工程证据；Reviewer 的作用是提供反例和复核材料，最后仍由 Main 综合。

### Remind：不是每个提醒都值得调用另一个模型

预算用了多少、时间还剩多少，可以从执行记录得到，不需要再请一个模型判断。

Remind 把这些事实和适当指导放进既有模型请求；Reviewer 则需要独立模型调用，提供另一种分析视角。提醒出现，不等于自动获得一次 Reviewer 调用资格，更不等于应该新增研究任务。

可以用一句话区分：**Remind 帮助 Main 注意执行事实，Reviewer 帮助 Main 检查判断，Runtime 决定哪些动作仍然允许执行。**

## 四、放进一项金融研究，协作应该怎样展开？

下面用一个教学案例贯穿这些设计，不把它当作一次已通过的真实金融研究验收：

> 我想增加一只 ETF。请比较它与现有组合的重叠，核对费用与主要风险，并给出适合或不适合加入的条件。

Main 首先需要确认用户目标与材料范围。随后，它可以把“近期披露有什么变化”“文件里的规则和风险如何解释”“已有数据下的组合重叠是多少”拆成不同的局部问题。

委派内容不能只有“帮我研究这只基金”。更清楚的任务是：核对指定产品的持续费用与一次性费用，保留份额类别、适用日期和原文依据，不需要重新做整份投资分析。

### 图 2：按问题与依赖协作，不按角色排固定流水线

![按问题依赖协作，保留直接交付与可选复核路径](../visuals/panorama-subagents/dependencies.svg)

这里，公开披露核查和文档阅读可以独立推进；依赖日期、单位等口径的计算，要等必要输入明确。数据已经齐备时，也可以直接计算，不需要等其他子任务全部结束。

图 2 中的复核是按需动作，不是发布的必经审批。Main 可以直接交付已有充分支持的分析，也可以先处理关键疑点。材料缺失时，则缩小相应结论的范围，不把缺口补写成事实。

**Main 综合的不是几篇报告，而是对原问题有用的发现。** 费用、重叠与风险应当共同回答“是否增加了用户需要的暴露”，而不是让每个执行者分别写一段正确却互不关联的文字。

最终的回答还需要讲清楚：哪些判断来自已取得的事实，哪些依赖用户目标与假设，哪些资料仍然缺失。这是上述教学场景的交付要求，不是让每次研究都强制执行同一套步骤。

## 五、成果交接：压缩过程，不能压掉依据

如果 Child 把完整搜索和调试历史交回来，上下文隔离就失去了意义；如果只交回一句结论，Main 又很难判断能否使用。

我们把交接看作一份可继续使用的工作成果，而不是一句“任务完成”。现有机制保留摘要、证据与产物引用、缺口，并允许阶段性成果先交回。Main 可以按需查看依据，不默认复制完整 Child 历史。

| 交回的信息 | 在金融案例中的作用 |
| --- | --- |
| **结论摘要** | 说明发现了什么，以及它回答哪个子问题 |
| **证据与口径** | 保留来源、日期、单位、范围，支持后续核对 |
| **计算或报告产物** | 让 Main 能使用真实结果，而不只是相信“已经生成” |
| **缺口与执行状态** | 区分已完成、部分可用、未执行和结果未知 |

这些是交接职责的概括，不是要求每次都填满固定格式。没有生成文件，就不应该为了完整而补一个产物地址。

### 图 3：局部失败不吞掉成果，也不自动变成成功

![局部失败、有限修复、明确缺口与证据回读](../visuals/panorama-subagents/handoff.svg)

可修复、且仍有预算与授权的错误，才进入有限修复分支。不能修复的部分进入明确缺口，已有合法发现仍可交回；已经取消或效果未知的操作，不能沿这条线被当作免费重试。

Main 取得摘要不等于读过全部原文。需要核实关键结论时，再走按需回读路径；能够独立使用的阶段性成果，也不必等整个 Child 结束才出现。

**历史报告交接还有一个反方向案例。** 2026 年 10 月下旬的受控研究记录中，Main 的实际模型输入已经包含用户选定的旧 Publication 全文及来源身份，但 Child 有自己独立的输入选取与物化步骤。若没有被实际选中的合法 `inputRefs`，继承的来源信息和授权并不会自动把这份报告复制进 Child 的请求。于是“Main 看到了全文”“Child 获准使用某类来源”“Child 完成了局部计算”都不能代替**Child 实际读过完整原报告**的证据。

这一观察限于所检查的历史报告接力，并不意味着所有普通结果引用交接都会丢失材料。后续还必须把历史报告的合法选取、真实 Child 消费和 Memory 遗忘后的内容资格一起核对；该完整验收目前不能据此宣布通过。

[LangChain Deep Agents 的 Subagents 文档](https://docs.langchain.com/oss/python/deepagents/subagents)同样建议返回凝练结果，不把原始数据和详细工具输出全部搬回主代理。我们在金融场景里尤其强调另一半：**精简的是过程，不是影响判断的口径和限制。**

## 六、三条交接边界：输入身份、局部工作与真实消费

### 输入与身份：同一份材料，不等于同一次消费

一次 Web Child 曾把工具结果引用和答案引用标记写到同一个字段。拒绝混用本身正确，但旧反馈暗示使用空数组，诱导模型删掉合法引用。我们修正的是**反馈对两类引用的解释**，而非放松来源校验；随后有真实模型样本交回有效引用，但整题仍因其他问题未完成。

并发还有轮次陷阱：`Main 第 1 轮 → Child 第 1 轮 → Main 第 2 轮` 的最后一步是全局第三条记录，却仍是 Main 的第二轮。曾有合法输入因此被拒绝；修复复用了执行体内部的进度坐标。**上下文隔离必须同时对应独立身份与轮次。**

一次真实 PDF 研究则说明另一层问题：图像已进入 Main 和 Child 请求，模型仍错读部分颜色、形状，跨材料核查也不完整。前面是交接与身份错误，这里是**输入抵达后理解错误**，不能把传图成功冒充金融判断正确。

### 局部工作：隔离过程，而不是复制 Runtime

Python Child 值得独立存在，是因为输入检查、局部调试、计算与导出构成一个工作单元。工作区绑定执行身份，Main 或其他 Child 只能通过获准产物交接，不能猜路径读取。2026 年 10 月 16 日的真实模型、合成数据实验中，Child 修复字段和 HTML 模板错误后导出报告，Main 发布下载入口，History 读回交付记录。这支持**完整局部交接**，不证明快于单 Agent 或金融算法全正确。

受管理的 PDF 专家仍复用 Child、Skill、`run_skill_script` 和 Analysis Sandbox。辅助脚本适配了 `data.pdfTables` 与 `data.items[].pdfTables` 的真实输入形状；返回零张几何提取表，只说明本次**没有交付可统计表格**，不能反推 PDF 无表格或视觉复核已完成。发现脚本不授予新代码执行权；[个人专家](agent-custom-expert-from-prompt-to-recovery.md)目前仍是文本 Profile，而非可任意上传执行的 ZIP。

Reviewer 检查遗漏和反例；Remind 提醒已有预算与时限。**提醒不是复核，复核不是审批**。Reviewer 的去重、单次在运行检查、冷却与影子模式限制无效循环；影子模式不自动向 Main 交付意见，但仍占用原预算。这些机制有受控工程证据，不等于多专家产生了净收益。

### 真实消费：提交、送模、采纳是三个问题

Child 交回摘要不证明 Main 的下一次模型请求收到了关键正文。2026 年 10 月 30—31 日的真实研究回查，用专家提交与后续 Main 输入作有限片段匹配，能证明**部分文字确实进入捕获的输入**，却不能证明全文到达、模型采纳或最终回答变好。样本分母和比对方法集中在[多专家贡献证据](agent-subagent-contribution-evidence.md)，全景不再重复数据表。

恢复时，Child 已提交、Main 已读到、工具效果已结算也各有自己的原回执。未知效果不能因为父进程丢了内存标记，就交给另一个 Child 免费重试；同 Run 接续沿原授权、冻结方法和原始效果身份。局部失败不能撤销独立合法的 Main 正文。

**Subagent 值不值得增加，取决于独立过程是否值得隔离，以及成果是否沿原身份被 Main 实际消费；不是系统里有多少专家名称。**

## 七、方法会变化，执行身份与原始输入要能重读

2026-10-24 的主干新增了用户自定义 Subagent Profile 的账户配置、方法版本与 Run 快照接线。它提供的是角色描述和方法指引，不是另一种 Child Runtime。Main 可在允许的目录里选择 Profile，原 A07 Child 消费这次 Run 冻结的身份、revision 与内容指纹；用户后来编辑或停用 Profile，不能倒过来改写旧 Run 曾收到的指引。历史读取仍要遵守当前查看者的账户权限。

此后，账户偏好、精确选择、目录与真实贡献展示、常用组合及 Child 自主描述修订都完成了有界工程验收，包含隔离 PostgreSQL 与脚本化模型的认证浏览器路径。这证明配置可以沿原 Child 身份被发现、选用和重读，不是自然模型的选角质量、实际投资研究效果或生产部署认证；个人角色仍不能扩大来源、预算、模型或交易权限。

与此相邻的[持久 HIL 机制](https://hpoenixf.com/eff-agent-article/articles/agent-durable-human-interaction-response-adoption)解决另一个实际交接：用户回复究竟有没有进入原 Child 的独立消息，而不只是进入 Main 的转述。Profile 约束“谁按哪一版方法工作”，HIL 验证“谁实际采用了哪条输入”，二者共同复用原 Child 身份和恢复。

### 投资视角仍是同一个 Child 的方法配置

2026 年 10 月的受控实现，将 Markowitz、Taleb、Bernstein 作为三种研究方法绑定到已有 Child，并未新增有交易权限的顾问 Runtime。方法 ID、版本与内容哈希随准入冻结；不同方法可以引用相同获准材料，恢复不能在旧执行里换方法。10 月 21 日的真实模型、合成投资题中，三种方法的结果进入 Main 并形成已保存正文，但同时出现过错选类型与重复委派。这支持方法绑定和交接，**不证明多视角比单 Main 更准确**。

### 统一角色入口，仍然要检查真实贡献

新建专家调用逐步统一到有版本身份的角色入口，历史执行保留原方法和原契约。这里复用的是准入、执行和成果交接机制，不能据此推出多专家研究一定更好。不同专家之间真正发生的依赖，仍要看原结果身份、获准输入，以及 Main 实际取得和使用的内容。

## 八、把协作收益、关键路径和总开销放在一起看

目前最明确的能力收益，是一段复杂局部工作可以拥有独立上下文、自己的工具过程和可消费的成果。主 Agent 不必默认接收整个调试现场，又保留了核对重要依据的路径。

有限并行提供了另一个机会，但它依赖任务关系。两个相互独立的子问题可以重叠执行；如果计算必须等待资料确认，多创建一个代理不会消除这条依赖。

依赖还需要区分模型希望怎样协作，与一次结果交接是否真的发生。比如“让下一位专家复核前一位的费率结论”可以是一条自然语言任务要求；但下游真正消费依据，仍要有原任务回执，以及 Main 实际等待/读取并传递合法的 `taskRef`、`inputRefs`。截至 2026 年 10 月 27 日，`relationHint` 已沿原请求封存并送达 Child；它依然只是**表达关系的软建议**，不启动等待、自动调度或兄弟 Child 的资料读取。真实依赖仍要由原 `taskRef`、获准 `inputRefs` 和实际回执证明，不能把这段字段当成工作流引擎。

Main 最初描述的任务也不一定始终正确。例如 Main 要求计算“精确持仓重叠”，但 PDF Child 发现一只基金只披露前十大。受控实现允许 Child 通过原 `submit_subagent_result` 的可选 `update`，自主修订本次 `task`、`hint`、`relationHint` 和合法输入引用；已接受的新描述只用于后续请求，不改写原用户文本、已派发请求、Run 授权或已提交结果。新增输入仍由原来源 Owner 决定能否使用。这是“研究描述可修，执行事实不可随意改写”，并不证明模型已经能稳定识别错误前提。更多账户侧选用机制见[自定义专家](agent-custom-expert-from-prompt-to-recovery.md)。

用一个理想化关系表示：

```text
串行耗时 ≈ 工作 A + 工作 B
并行耗时 ≈ max(工作 A, 工作 B) + 委派、等待和汇总开销
```

这只是取舍模型，不是 ETF Agent 的实测曲线。实际还受到模型与工具并发、重试和任务依赖影响。

总 token 也一样。Main 少携带局部历史，不意味着系统总量更少：Child 的输入输出、重复背景、交接和必要回读都要计算进去。

Anthropic 在[《How we built our multi-agent research system》](https://www.anthropic.com/engineering/multi-agent-research-system)中同样指出，多代理研究会增加 token 消耗；大量共享上下文、依赖密集的任务，并不天然适合多代理。我们借鉴的是这种适用条件判断，不把他们的效果数字移植为自己的收益。

我们也有真实反例：Child 完成了有效引用交接，但 Main 反复查看状态、取消后重新委派，最后到达轮次上限，没有发布答案。该次还伴随供应商流中断，不能把全部失败归到协作策略，却足以说明局部成功不保证整体交付。

完整任务的评价维度包括：Main 上下文减少了多少、总开销增加了多少、结果是否真正被消费，以及用户的问题有没有得到回答。

### 哪些任务值得并行，哪些会被交接成本吃掉？

| 任务形态 | 更合适的起点 | 原因 |
| --- | --- | --- |
| 查一个明确字段、做一次稳定计算 | Main 直接使用工具 | 独立上下文的收益可能小于准备与交接开销 |
| 大量检索、局部调试、长篇文件核查 | 一个自主 Child | 过程长，交回的结论与依据可以相对紧凑 |
| 几个材料范围清楚、彼此独立的子问题 | 有限并行 Child | 可以重叠工作，但仍需共享资源与主问题 |
| 必须持续共享大量背景、下一步强依赖上一步 | 先保留顺序，由 Main 组织 | 多份独立历史容易重复背景，不能消除依赖 |
| 结论已有，缺少关键反例或第二种方法 | 按需 Reviewer 或另一个研究视角 | 价值来自问题与方法差异，不能由角色数量推断 |

这张表提供起点，模型仍应根据实际材料修订拆分。一个“读 PDF”的局部任务可能需要网页核对；一个计算任务可能发现输入口径不成立，先交回限制比继续算出一个精确但无意义的数字更有用。

## 九、从一个能完整交接的 Child 开始

不必从四种角色一起开工。更合理的起点，是选一个局部过程较长、成果容易检查的任务，先跑通一条完整链路。

**先做一个通用 Child。** 它应有独立上下文、执行身份和多步工具循环，能提交成果，也能被取消和在支持的边界恢复。不要先复制四套只有名字不同的 Agent。

**再增加专业方法。** 区分“什么时候值得委派给它”“它处理问题时应关注什么”“本次实际能调用什么”。这些信息可以分别落在角色描述、方法指导和工具授权中，不必把全部规则塞进角色名称。

**然后把交接做实。** 不只测试 Child 有没有返回文本，还要测试 Main 能否读回依据、使用计算结果或打开实际产物。合法部分成果与失败、未知状态都要有表达方式。

**最后复用已有治理。** 我们已有预算、收尾、授权与恢复模块，Subagent 接入这些机制，而不是各领一份新资源。多个 Child 争用剩余额度、Main 结束后仍有任务在运行、结果已提交但尚未消费时发生中断，都是需要检查的具体路径。

完整能力不意味着每件事都要委派。简单查询、一次工具调用，或者高度依赖整段对话的工作，留在 Main 可能更合适。**是否使用 Subagent，应由任务能否从隔离与自主工作中受益决定，而不是由系统里已经有多少种角色决定。**

### 接上来源核对专家之后，发布权仍留在 Main

上面的 `fixture-child` 是保留的历史小例子。公开 v0.15 增加了串行 `source_check`：Child 在自己的上下文中读取限定的 Atlas A/B 页面，把原文和派生核对意见交回 Main，再由 Main 整理报告。它不是本文全部专家角色或并行编排的公开实现。

这个组合后来暴露了一个接缝：Main 启用 Publication 时，把父级绑定完整交给只读 Child，会与 Child 自己的发布配置冲突。**v0.15.1 修的是能力收窄，而不是取消身份检查。** [specialist-child.mjs](https://github.com/hpoenixf/open-etf-agent/blob/8ba24a15cb1ce6ad3a0ebd48141be0549bfda35a/src/specialist-child.mjs) 只移除精确匹配的 Main-only Publication 绑定，其他绑定保持不变；交接回读也检查同一份受限身份。Child 仍不能发布，Main 则能沿原路径发布自己的正文。[组合回归](https://github.com/hpoenixf/open-etf-agent/blob/8ba24a15cb1ce6ad3a0ebd48141be0549bfda35a/test/specialist-publication.test.mjs)同时检查了交接、Main 发布和终态再次读取不触发重派。

想观察来源交接，可在[当前公开固定版](https://github.com/hpoenixf/open-etf-agent/blob/34124cefc6df289e08518173789210b45a716451/src/specialist-cli.mjs)按其 README 安装后，用新的 Session 目录运行：

```bash
node src/specialist-cli.mjs run --session runs/article-source-check
node src/specialist-cli.mjs read --session runs/article-source-check --run RUN_ID
```

将首条命令返回的实际 `runId` 填入 `RUN_ID`，对照 `child.summary`、`sources` 与 `report.text`。这个默认示例是离线脚本，保存并回读报告，**没有启用 Main Publication**；发布组合另见上述回归及[该版独立真实模型验证说明](https://github.com/hpoenixf/open-etf-agent/blob/8ba24a15cb1ce6ad3a0ebd48141be0549bfda35a/docs/verification/v0151-runtime-repair.md)。真实模型使用的仍是合成任务，不能由此推导金融专家效果。旧 `fixture-child` 覆盖标记保持原资格，新的源码关联不冒充一次覆盖重跑。后续使用入口见[当前 main](https://github.com/hpoenixf/open-etf-agent)。

## 十、让局部自主服务于整体交付

**任务值得委派，不在于角色名称有多专业，而在于它能否独立完成一个有价值的工作单元，并把依据带回主问题。**

下一次设计子代理，我会先问：

1. **这项工作真的需要隔离吗？** 简单查询、一次计算或强依赖 Main 全部上下文的任务，直接执行通常更合适。
2. **交回的是什么？** 不只是“已完成”，还要有可读取的来源、口径、计算或文件结果，以及明确缺口；Main 必须实际消费。
3. **值得付出额外成本吗？** Child 的模型调用、等待、重复读取和综合都算成本。局部成功不自动变成用户任务完成，更不能由此推导金融质量提升。

ETF Agent 的经验是：**分离局部过程，保留关键事实；专业分工可以灵活，最终交付责任不能散。** 这比让更多 Agent 同时忙碌更值得追求。
