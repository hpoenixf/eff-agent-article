# 资料明明在，Agent 为什么读不到？

你把一份新版退货手册交给 Agent，问「定制商品什么时候还能退？」它告诉你没有找到相关内容。你打开附件，翻到「订单取消与例外」，那段条款就在下面。

下次遇到这种情况，可以把任务缩成一个能核对的请求。

> 请直接打开我上传的新版退货手册，找到“订单取消与例外”这一节。先摘录与定制商品有关的原句，标出页码或章节，再回答什么情况下能退。如果打不开，请说明你卡在哪一步。

这个问法把找文件、读原文和解释规则拆开了。在自家产品里排查时，也可以沿着这几步，找到下一处值得修的地方。

## 搜索结果是空的，接下来怎么读？

在 2026 年 11 月的多 Agent 补测中，我们回看了四个读取受阻的案例，逐一检查它们的首轮文件搜索。模型使用的字面关键词在对应的已授权材料里都不存在，搜索返回空列表，下一轮请求里也确实是空列表。

接着我们查看了文件目录的生成过程。负责管理文件的系统已经知道这些材料的精确位置，发给主 Agent 的目录却只有文件记录，没有带上可用于读取的位置。模型有搜索和读取工具，但当时也没有单独查询文件元数据的工具可以用。**文件有，读法也有，缺的是把位置交给模型的那一步。** 这类困难也出现在显式委派补测中，子 Agent 可能接手后继续寻找同一个入口。[多 Agent 测评背景](agent-multi-agent-value-evaluation.md)

手册例子里的「退货」与「取消」说明了字面搜索为什么会走到这里。换同义词、缩短查询，适合在大批材料中继续寻找线索。用户已经指出具体文件时，还可以沿目录直接读相应章节。搜索引擎也有类似的两条入口。例如 Elasticsearch 提供按文档 ID 读取原文的接口，适合目标文档已经确定的场景。Agent 要用上这类入口，需要先收到可用的文档位置，再调用原有读取工具。[Elasticsearch 按 ID 读取文档](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-get)

## 把已知位置交给 Agent，让它读一次

用开头的手册做个简化示例。目录里有「新版退货手册」，系统也知道这份小文件在工具里对应一个可直接读取的位置。拿到目录里的地址，Agent 就可以打开文件，取得正文，再从正文判断例外条款。

在我们的实现里，主 Agent 和子 Agent 各自接收自己有权看见的文件目录。对于只有一个可读片段的材料，目录可以带上文件系统已确认的准确位置，例如 `record:1`。读取工具随后仍要检查本次任务是否获准读取该文件和片段。目录给的是地址。正文进入模型输入，要等到读取成功。

这也给出了几种取舍。两三份短文件可以直接送入上下文，少一次读取。材料长、涉及多个版本，或者子任务只能看一部分时，先给有用的目录，再按需读正文，更容易控制范围和请求大小。多片段文件还要考虑目录如何分页，以及模型能否知道当前列表只展示了一部分。我们这次修通的是有准确位置的单片段路径，已验证主任务和子任务可以沿各自的权限去读。修复后的真实模型回答质量仍待复测。

## 用四步找到断点

| 看到的现象 | 接下来查什么 |
| --- | --- |
| 搜索返回空列表 | 看实际发出的关键词、查询范围和文件版本。目标文件已知时，试走目录或准确位置。 |
| 看得到文件名，打开时却报错 | 看模型实际拿到了哪个位置，工具是否接受这种位置，以及该任务有无正文读取权限。 |
| 工具显示读取成功，回答仍说找不到 | 看下一轮模型输入里有没有那段正文。成功回执、文件名和原文是不同的信息。 |
| 回答引用了原文，结论仍然可疑 | 打开引文所在的版本和章节，核对例外、适用条件，以及那句话能支持多强的结论。 |

对用户来说，最快的检查是**请它从你指定的文件摘出原句，并给出可回查的位置**。你手上有对应页、Agent 仍打不开时，可以单独给它那一页，再核对它怎样解释。

对开发者来说，可以把同一个例子写成回归测试。让首次搜索有意零命中，由系统真实提供位置，让 Agent 发起读取，再检查原文是否到达下一轮请求。用同一份文件跑一次缺少读取权限的情形，就能同时核对这条阅读路径和它的权限边界。
