# 上下文快满时，为什么不能直接把历史交给模型摘要？

一次基金研究已经翻过数十份资料，Main 还需要继续分析。最简单的办法似乎是让模型“总结旧对话，再接着做”。但我们遇到的真正危险不是总结不够短，而是**一句流畅的摘要，把“模型曾经提议”写成“工具已经执行”，把“上季度数据”写成“最新事实”**。

还有两个更反直觉的问题：保守容量预检可以把所有有收益的摘要挡在门外；检查点已经保存摘要，也不表示摘要进入下一次真实模型请求。最后我们没有做一个更强的“总结 Agent”，而是把摘要降级成**非权威工作便笺**，让原有 Run、工具、来源和恢复记录继续掌握事实。

## 一、不是所有上下文压力，都该靠模型摘要

我们把减负分成有先后顺序的三件事：**旧工具结果外置 → 可逆拟合和精确回读 → 必要时才有损摘要**。同一份 PDF 或基金持仓表，若已有原版本和合法选区，不该在每轮重复搬进请求；最近的工具调用及结果必须成对保留，不能只删结果、留下“曾调用”的空壳。

[Anthropic 的上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)也强调上下文是有限工作空间。它提供的[工具结果清理](https://platform.claude.com/docs/en/build-with-claude/context-editing)很适合无需继续查看旧输出的任务。我们的金融研究要额外保证：**清掉模型当前视图，不等于清掉可核验的来源、授权或数值**。

## 二、最意外的阻碍：越保守，反而越压不动

现行应用压力策略按完整请求 UTF-8 字节计量：默认软阈值 256 KiB、期望目标 224 KiB、最低净节省 4 KiB，摘要上限 6,000 字节。这是应用策略，**不是提供商的 token 上下文窗口**。

早期预检先假设“模型可能写出最大、最难转义的摘要”，然后将这个假想产物放回请求；只要达不到目标，就拒绝发起摘要。即使模型实际能写出很短且有收益的摘要，也永远没有机会尝试。另一条规则把软目标误当成硬门：省了可观空间却仍未一步降到目标线以下，也直接拒绝。

现在区分两道判断：**尝试前排除不可能，生成后检验真实收益**。如果连最短的有效非空摘要也不可能满足最低节省或真实硬输入上限，就不花这次模型调用；否则允许候选进入原 Gateway。实际完成后，把摘要、工具定义、引用目录、最近工作集与原用户纠正组成**完整下一次 Main 请求**，再检查实测净节省、硬容量和身份授权。软目标只是想留的余量，不阻止安全的渐进缩减。

## 三、摘要最危险的能力：冒充原执行事实

例如用户要求比较两只基金，工具只返回部分季报；用户随后补充“不能用旧净值代替今天的价格”。自由摘要可能写出“已读取最新季报、完成净值核验”，让后继模型错把它当作执行回执。

我们只选**同一个 Run 内较早、完整、已结算并有持久身份的调用组**；未完成、未知效果、用户原文与纠正、最近工作都保留原样。旧摘要不递归变成新摘要的来源。财务数字、工具结果、来源、剩余预算、已提交正文仍由它们各自的原 Owner 投影，模型编写的摘要不能取得新的来源许可。

这也解释了为什么“压缩率高”并不够：若压掉了是否执行过工具、哪份结果属于哪次调用，后面的研究会在更短却更假的上下文中继续。

## 四、现在实际怎样运行：摘要要经历三次不同的确认

1. **是否值得试**：只有可逆拟合后仍有压力、存在安全旧区间、最小摘要仍可能满足原硬容量和净收益，才走原请求准入。
2. **是否值得采用**：摘要模型实际结束，未发生截断；在完整请求上重新拟合，确认净节省、真实硬限制、源区间与当前 Run/纠正身份均成立，然后由 Recovery 提交检查点。
3. **是否真的使用**：后继 Main 请求必须确实携带该摘要。恢复从原 checkpoint 读回已提交记录，不重新请求模型，也不重做已结算工具。

\`\`\`mermaid
flowchart TD
  A["完整 Main 请求"] --> B{"仍有容量压力？"}
  B -- "否" --> Z["保留原请求"]
  B -- "是" --> C["选择已结算旧组"]
  C --> D{"最小摘要仍不可能获益？"}
  D -- "是" --> Z
  D -- "否" --> E["原 Gateway 生成有界摘要"]
  E --> F{"真实完整拟合有净收益且合法？"}
  F -- "否" --> Z
  F -- "是" --> G["提交原身份 Checkpoint"]
  G --> H["后继 Main 请求实际使用"]
  H --> I["必要时按原引用回读来源"]
\`\`\`

摘要是一次真正计费的模型请求，也要遵守原 Gateway、deadline、路由输出限制、请求扣账和收尾预留。一轮真实摘要曾因为额外写死的 900 输出 token 上限以 \`finishReason=length\` 结束，故不采用；当前不再单设更小的内部上限，而是使用已拟合 Main 与实际路由的界限。结果不合格则继续原历史，不重试到“看起来成功”。

另一真实 Run 中，完整拟合请求由 264,062 字节缩到 182,786 字节，且后继 Main 确实携带摘要。两次来自不同研究，不能当作质量或成本改善的 A/B 证明。真正有意义的观察不是“摘要文件存在”，而是“原请求改了什么、模型最终收到什么、原件是否仍能读回”。

## 五、别人的方案，以及我们为什么没有全盘照搬

| 方案 | 擅长的场景 | 我们为什么另做一层 |
| --- | --- | --- |
| [LangChain SummarizationMiddleware](https://reference.langchain.com/python/langchain/agents/middleware/summarization/SummarizationMiddleware) | 达阈值后总结旧消息，保留近期消息和 AI/Tool 对 | 框架帮忙管理对话窗口，但原金融数值、Run 授权、已执行效果与冷恢复还需要业务自己负责 |
| [Anthropic Context Editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) | 清掉老旧工具输出，降低模型工作区负担 | 清除旧文本很有效，但不能凭清除动作建立我们自己的原始回执和来源身份 |
| **ETF Agent Main 压缩** | 可逆外置优先，有压力才摘要，摘要无事实权威 | 工程复杂，必须做身份和恢复检查，但避免把简写误当数据库 |

**我们的目标不是造出比框架更会总结的模型，而是让总结错误不会冒充新的持久事实。** 这条设计特别适用于带金额、日期、实际工具执行和后续追责的长研究。代价是即使字节减少了，也不能因此宣称模型更聪明、结论更准。


## 六、一个能自己跑通的公开实验

[Open ETF Agent](https://github.com/hpoenixf/open-etf-agent) 的固定教学快照把其中一段做成了可运行的实验：合成资料在显式字节压力下生成派生便笺，后继请求先消费便笺，再用原 \`resultRef\` 读取原页面并保存报告。它展示的是**工作便笺被采用，原件却仍保留原身份**，不是私有 Main Recovery 的全量开源实现。

\`\`\`bash
git clone https://github.com/hpoenixf/open-etf-agent.git open-etf-agent-compaction-demo
cd open-etf-agent-compaction-demo
git checkout --detach 05c0dd2dc550f4f7e5da034340ff5c3159768fcf
npm ci --ignore-scripts --no-audit --no-fund
npm run demo -- --case compact-and-reread
\`\`\`

检查生成目录中的 \`run.jsonl\`、\`report.md\`、\`manifest.json\`。便笺为 \`derived-summary\`，展示性的上下文调用对带有 \`projectionOnly\`，不会假装工具真的再次执行。较晚的独立固定快照还有[跨进程便笺恢复](https://github.com/hpoenixf/open-etf-agent/blob/ff5b9273ef0d239e804f61792702cd2e94174be7/test/durable-runtime.test.mjs)与[已提交效果回执保留](https://github.com/hpoenixf/open-etf-agent/blob/8ba24a15cb1ce6ad3a0ebd48141be0549bfda35a/test/compaction-receipts.test.mjs)用例；不同版本的能力不要混写为一次验收。

**下次设计类似机制时，先问哪段历史能被精确回读，再问哪段旧工作适合被有损总结。只有读不到原始事实时，摘要才会从“节省上下文”变成“制造另一套事实”。**

## 延伸阅读与交流

**不要混淆两类摘要：** 本文聚焦一次 Run 内旧工具回合的 Checkpoint；[跨 Run 会话压缩](/articles/agent-conversation-history-compaction-source-boundaries)则把同一 Conversation 已完成的旧问答对按来源身份、不可变摘要和容量投影交给后续 Run。两者的最终负责事实、失败回退和验证范围不同。
