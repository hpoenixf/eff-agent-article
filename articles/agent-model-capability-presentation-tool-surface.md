# Agent 有这个工具，模型为什么还是看不到？——工具表面的演进

做一次产品比较，系统已经登记了“搜索产品”和“读取产品资料”两个工具。你希望模型先找对象，再读取详情。可如果它只看到搜索，提示词再强调“核对原始资料”也不会补出缺失的接口。

另一个方向更隐蔽：本轮原本只准入一组工具，后续请求装配却改了其中的参数定义。模型能生成符合新定义的调用，不代表执行宿主认可这份接口。

这里用产品比较作为教学场景。本文要回答的是：**怎样把“这轮应当呈现什么”准确送到模型，而不是只证明注册表里有这个工具？** 当前方案是沿原准入事实生成独立基准，在可变装配前后核对，并让失败回到原执行流程。它没有再造一套能力管理服务。

<span id="一、最初的问题-skill-说有工具-模型却用不了"></span>
<span id="二、工具定义集中之后-仍要确定谁有权决定可见性"></span>

## 1. 先分清工具经过的四个位置

| 位置 | 能回答什么 | 不能由此推出什么 |
| --- | --- | --- |
| 供应商或 MCP 注册 | 名称、说明和输入 Schema 是什么 | 本次任务已经获准使用 |
| 原 Run 与宿主准入 | 本次执行在原授权、范围和阶段下可用哪些能力 | 后续请求一定原样呈现 |
| 模型请求的工具表面 | 这一轮实际交给模型哪些完整描述符 | 模型已调用，或调用必然获准执行 |
| 宿主派发与回执 | 哪个具体调用实际被执行、拒绝或尚不确定 | 研究结论正确、材料已被模型理解 |

“工具表面”（Tool Surface）处理第三行与前两行之间的一致性。执行前的真实参数、资源和访问检查仍在原工具宿主，不因模型看见工具而省略。

历史上确有一个接入缺口：2026 年 9 月 27 日，产品跟踪 Skill 已声明两个 Market MCP 方法：

```text
market__search_instruments
market__get_instrument_profile
```

但当时 Research Action 与 Native 静态工具合同没有承接它们。下面是那次源码检查确认的断点，不是线上用户事故归因：

```text
Skill 声明支持
      ↓
MCP 已经注册
      ↓
Native Research 没有对应工具
      ↓
模型无法通过这条路径调用
```

接入后，另一种错位也被受控路径重现：能力推导宣称 Market 可用，宿主网络策略却不一定允许对应动作。反过来，关闭 Web 搜索也不应顺便关闭结构化 Market 数据。**声明、可见和可执行必须各有来源，不能靠一个“已启用”布尔值包办。**

当前业务工具描述来自 MCP；原 Run grant 与宿主给出准入，工具表面负责本轮呈现。只在 Skill 中提到一个方法，不再等于有权隐藏同域另一个已经获准的普通方法。早期共享 Web 路由上的精确工具上限曾有必要，但接口归属变化后，不能把旧名单继续当成新的权限来源。

## 2. 一轮请求现在怎样组装

工具表面不是对最终数组做一次比较就结束。当前主要路径如下：

| 步骤 | 做什么 | 为什么放在这里 |
| --- | --- | --- |
| 原准入结果进入投影 | 取得完整名称、说明、Schema 与顺序 | 不从 Skill 文字或任意诊断字段重新授予能力 |
| 独立复制基准 | 在可变 Hook 前保存获准描述符 | 防止后续修改连比较标准一起改变 |
| 扩展投影后早检 | 核对工具和受保护控制输入 | 先识别非法改动，不能靠后面的合法重组洗掉它 |
| 原负责模块合法收窄 | 按既有阶段、资源等决定调整本轮集合 | 收窄只能来自原合同，不能扩入未准入工具 |
| 再保存独立基准 | 固定收窄后的描述符 | 给后续上下文、证据与异步准备提供比较依据 |
| 分离控制对象并终检 | 在后期准备后检查实际逻辑请求 | 既防后期漂移，也隔开留存的可变别名 |
| 原模型调用层发送 | 转换成提供商协议 | 逻辑一致不等于各协议的 wire 字节相同 |

比较的不只是工具名称，还包括数量、顺序、完整说明和输入 Schema。只核对名字，无法发现 `query` 从字符串变成数字；只核对 Schema，又可能遗漏对模型选择有影响的描述变化。

回读工具 `read_tool_result` 也遵守同一原则。它可以由原宿主或上下文拟合路径按条件准入，但不能因为 Hook 把这个名字塞进请求，就反过来获得资格。

保存最终请求的封存记录仍然有用，但它回答的是“准备了什么”，不是“什么获准了”：

```text
被修改的实际工具
       ↓
封存被修改的工具
       ↓
用封存记录校验实际请求
       ↓
错误也可能通过
```

独立基准、最终请求和封存记录可以关联，却不能互相冒充。

## 3. 深度比较为什么会比较出一个假相等

最容易忽略的不是比较算法，而是比较双方是否独立。

一个受控回归构造了这样的情况：供应商的嵌套 Schema 中，`properties.query` 原本要求字符串；Hook 将它原地改成数字。如果期望值与实际请求都指向同一份嵌套对象，它们会同时变化。比较器再严格，也只能看到“两边都是数字”。

浅复制外层数组不能解决这个问题。当前在进入可变投影前，对已准入的完整工具描述符作独立复制。后面的合法收窄形成新基准后，也再次复制，避免后期装配共享同一份标准。

这与检查时和使用时不一致的 TOCTOU 问题相似，但这里的证据是受控请求修改与对象别名，不是已证实的生产并发攻击。

早检与终检因此各有作用：早检防止非法修改被后面的重组掩盖；终检检查后期异步准备是否又改变了请求。即使没有可选 Hook，后期装配仍然存在，终检也不能随开关一起消失。合法的消息压缩只改变消息，不应被误判为工具描述符漂移。

## 4. 最后一次检查之后，为什么还要分离对象

“已经在适配器末尾检查了”听起来足够，但适配器并不一定直接写网络请求。它后面的 Factory 封装仍可能先等待一次异步操作，再进入模型 SDK。

沿实际 SDK 序列化边界的受控回归发现：Hook 保留了请求对象的引用；适配器检查结束后，这个引用仍能追加未准入工具或改写说明。结果可能是记录中的旧工具哈希没变，真正准备发出的工具却已经不同。

当前处理不是继续在每层加一个新的授权器，而是在最后检查前**分离可变控制对象**：复制请求外壳和消息数组，深拷贝工具描述符、输出 Schema、推理配置等控制值，再检查将被后续路径使用的对象。旧 Hook 留下的引用不再能借同一个控制对象改写发送内容。

那为什么不把整份请求深拷贝，简单一些？因为图像、压缩和证据来源的一些关联依赖消息对象身份，保存在 WeakMap 等旁路结构里。把所有消息统一换成新对象，正文看似还在，证明它从哪里来的关联却可能丢失。这里保留原消息路径所需的身份，专门需要复制的来源信封仍由自己的路径承接证明，不能靠通用 JSON 克隆代替。

这是一个有代价的取舍：控制值独立，数据身份由原负责模块维护。新增控制字段时要明确复制与核对责任，不能宣称“复制过请求”就保护了所有正文语义。相关回归检查了真实 SDK 的序列化内容，但使用合成传输，不是一次真实模型质量评估。

## 5. 工具少了，什么时候是正确结果

完整呈现不是要求每一轮永远保留同一份名单，而是要求**合法变化有原负责模块的依据，必需工具不被随意删掉**。

三个情况值得分开：

- **阶段或资源变化**：原合同可合法收窄本轮工具集合。无论怎样收窄，都不能凭装配结果扩出新能力。
- **上下文容量不足**：必需工具放不下，应给出明确容量结果，而不是默默按 Top-N 截断业务工具。当前已有显式可选的进度通知工具可在特定容量失败后省略，这不是允许 Hook 任意删工具。
- **可信的可用性变化**：搜索额度耗尽可能只关闭搜索，仍允许读取已有合法 `sourceRef`；整体 Web 截止时间则可能同时限制两者。判断来自原 Web Gateway/宿主绑定本次执行的事实，不是任意工具结果里一个形似“额度用完”的字段。

最后一种区别来自真实受控反例：一个与 Web 无关的 MCP 结果带上类似额度诊断，就曾让恢复路径错误隐藏 Web 搜索。修复应回到原可用性来源，工具表面不能另建预算缓存，也不能借“重新验证”发明一套同 Run 的新授权规则。

Entry 的能力摘要同样只是摘要。可以访问持仓，不代表已经读取持仓；获准使用文档引用，也不代表取得正文。Research 的完整描述符与 Entry 的受限能力提示服务不同位置，不能把一份元数据当成读取成功的回执。

<span id="五、拒绝失配请求-也要结清它的执行事实"></span>

## 6. 拒绝请求之后，还缺一件事

一份失配请求已经被阻止发送，检查是否就结束了？不一定。进入准备阶段时，原运行流程可能已经建立了请求身份和资源预留。

受控异步准备回归曾发现：适配器正确拒绝派发，却漏掉原请求的确定未派发记录。只抛异常，不会自动结清这份预留。

当前失配沿既有 `onProviderRequestFailure` 回调报告 `pre_dispatch_rejected`，由原 Main/Child 请求账本处理。没有相应持久化生命周期的适配器调用，只能报告本地协议失败，不能把回调返回等同于“一定有一笔持久预留已结算”。

```text
工具表面失配
      ↓
仅拒绝当前模型请求准备
      ↓
原请求 Owner 记录确定未派发
      ↓
原 Runtime 决定继续、恢复或终结
```

检查只拒绝本次不合法的请求装配。原运行流程决定能否继续、恢复或终结，已合法生成的独立正文不因这一次请求失配而被工具表面删除。

可迁移的判断是：增加一道拒绝检查时，也要找到原系统记录“不曾发生”这件事的位置。否则访问边界保护住了，生命周期可能留下悬空状态。

## 7. 什么时候直接用 SDK，什么时候需要这层保护

成熟 SDK 已提供动态选择工具的机制。以下是按今天的需求作比较，不是声称项目当时对这些方案做过同题试验。

| 机制 | 更适合的问题 | 应用仍需决定什么 |
| --- | --- | --- |
| OpenAI Agents SDK 的 `is_enabled` | 按上下文、偏好或运行条件启用工具 | 参数与资源层授权仍归实际工具；哪些应用规则决定可见性 |
| Vercel AI SDK 的 `activeTools`、`prepareStep` | 保留完整类型注册表，同时按步骤选择子集、调整消息或模型设置 | 哪些变化是本轮预期配置，哪些是自己装配链中的非法漂移 |
| MCP 的 `tools/list`、变更通知与 `tools/call` | 标准化供应商发现、描述和调用 | 如何把发现结果接到本应用的任务准入与最终请求 |
| 本文的独立基准与分离检查 | 多个可变扩展、上下文处理和异步封装共用一轮请求 | 维护复制边界、合法收窄规则及原请求的失败结算 |

[OpenAI 的条件启用文档](https://openai.github.io/openai-agents-python/tools/#conditional-tool-enabling)也明确区分可见性与依赖具体参数、资源的授权。[AI SDK 的工具调用文档](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling#active-tools)展示按步骤选择工具；[MCP 2025-06-18 工具协议](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)则定义发现与调用的基础接口。它们与应用的一致性检查是不同层，不能因没有本项目的内部字段就判为能力不足。

如果只有少量固定工具，构造后直接调用 SDK，也没有共享可变扩展，显式配置和工具内部授权往往更简单。本文的额外复杂度来自我们自己的长装配链：需要保留扩展和上下文处理，又要防止它们改变独立准入事实。代价是复制、比较和更多边界测试，而不是白得一套更可靠的模型。

## 8. 从一个小的公开用例开始核对

### 直接看 Child 每轮收到的工具集合

固定公开快照的[只读 Child 用例](https://github.com/hpoenixf/open-etf-agent/blob/e1b8e4edde724548fab16d8ca4b205379bfa7f30/test/cooperation-integration.test.mjs)把可见性落到真实 Gateway 调用参数：不是检查注册表里“有什么”，而是记录每轮实际呈现了什么。

在所链固定快照按 README 安装依赖后，运行：

```bash
node --test --test-concurrency=1 --test-name-pattern='^3\.4 fixture child shares root counters and advertises only allowed read tool$' test/cooperation-integration.test.mjs
```

两次脚本模型调用都只能看到 `read_page`，最终根计数是两次模型、一次工具；Child 返回派生结果，没有自行保存报告的回执。终端的精确测试结果对应这些断言。

这只是受限 Child 的工具呈现与共享计数，不是完整的模型能力呈现与动态工具表面编排，也不证明真实模型会选择正确工具。

## 9. 下次排查先问什么

看到模型没用某个工具，先定位四件事：工具是否被发现、本次执行是否准入、本轮请求是否真的呈现、具体调用是否派发。不要直接从“模型没选”倒推权限错误，也不要从注册成功推断工具已交付。

需要检查请求装配时，保留三类测试：非法描述符变更必须拒绝，合法消息拟合必须通过，拒绝后原账本必须记录正确结果。还要把异步等待放在检查之后，试着通过保留引用改对象；只在函数返回前比一次数组，可能碰不到真正的发送缝隙。

这正是[原则 2「复杂度必须归属正确的 Owner」](/principles#principle-2)在这里的含义：给最终工具呈现一个清楚的负责者，而不是复制所有授权和预算。用[方法 3「证据传递与投影」](/principles#method-3)分别核对准入依据、实际请求与派发回执，才知道这一次到底少了哪一环。
