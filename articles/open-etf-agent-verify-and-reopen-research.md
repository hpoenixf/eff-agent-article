# 从第一次提问到重新打开：用 Open ETF Agent 做一次可回看的研究

<LearningPathNav />

你问：「ETF 为什么会溢价或折价？」看到答案之后，想核对的是三件事：它读的是哪段原文？哪些话只是它自己的解释？刷新页面后，看到的还是刚才那份回答吗？这三件事和回答长不长没有关系，却决定了你能不能在这份回答上继续做研究。

[上一篇](https://hpoenixf.com/eff-agent-article/articles/open-etf-agent-research-workbench)讲了会话、追问、每日对照和独立账户。这篇从 v0.44.0 到 v0.47.0，走一条更短的路线：问一次，核对一次，再找回原来的回答。

## 先在本机练一次：刷新页面不是重新研究

用 Node.js 26.8.1–26.x 和 npm，安装 [v0.47.0 固定版本](https://github.com/hpoenixf/open-etf-agent/releases/tag/v0.47.0)：

```bash
git clone --branch v0.47.0 --depth 1 https://github.com/hpoenixf/open-etf-agent.git open-etf-agent-reading
cd open-etf-agent-reading
npm ci --ignore-scripts --no-audit --no-fund
npm run gui -- --project ./test-output/local-gui --port 4179
```

打开命令打印的本机地址，新建会话，选内置的模拟跟踪资料，再输入：「这份资料讲的是 ETF 跟踪表现，还是交易价格？」离线脚本不会理解问题，也不会查真实行情；它按选择的样例生成带原文的报告。这里练的是操作：点「核对来源」，打开保存的报告，再刷新页面，从历史重开同一轮。也可以停止服务，用同一项目目录和端口再启动。原问题、报告和引用应该仍能打开，不用再次发送问题。

从 v0.44.0 起，保存的 Markdown 报告在工作台里直接排版。后来界面把输入固定到底部，历史和来源可以独立收起，窄屏上也不用一直给侧栏留位置。图表是可选的：图里的日收盘价取自同一轮工具数据，缺值就留空，不从回答里猜数字。下面这个概念核对不需要图表。

## 到在线工作台：先问原文说了什么

如果已经按[在线工作台指南](https://github.com/hpoenixf/open-etf-agent/blob/v0.47.0/docs/local-gui-live.md)配置了有权使用的模型和公开网页工具，可以用独立的在线项目，拿 [Investor.gov 的 ETF 投资者公告](https://www.investor.gov/introduction-investing/general-resources/news-alerts/alerts-bulletins/investor-bulletins-24)试一个不依赖实时行情的问题。把公告链接和这段问题一起发送：

> 只根据这份公告，解释 ETF 的交易价格和每份净值有什么区别，为什么会出现溢价或折价。请说明真正读到的依据。读不到的地方直接指出，不要查今天的行情。

这是供读者尝试的示例，本篇没有为它另跑在线测评。如果网站没返回可读原文，也可以观察工作台怎样呈现这个缺口。内置离线模式不会访问这份公告。

**怎么选模式？** 只有一个已知来源和一个明确问题，先用「标准」；不确定需不需要查资料，可以用「自动」；要对照投资者公告、招募说明书和交易所口径，解释它们各自能证明什么，再选「深度」。这三档从 v0.45.0 起在输入区可选。思考强度是另一项模型设置，只有支持的配置才显示；它不是深度研究的另一个名字，也不能保证答案正确。

## 看进度时，别把三种证据混在一起

| 工作台里的事实 | 可以据此判断什么 | 不能据此判断什么 |
| --- | --- | --- |
| 找到一个搜索结果 | 有值得核对的线索 | 不能说已读原文 |
| 网页返回了可读片段 | 这一轮拿到了那一段文字 | 不能说读完整页，也不能证明解读正确 |
| 正文已保存且能重新打开 | 原来那份答复确实交付并可回看 | 不能说金融事实、推导和因果关系已审过 |

从 v0.46.0 开始，深度研究的进度把「读到原文」「检查过但没拿到可读原文」「正文保存并读回」分开。假如实际读到的片段只说明交易价格可能高于或低于净值，就用它支持这一点。没有读到解释套利机制的段落，就标成尚未核对，而不是拿搜索摘要把论证补齐。

网页有时较长。v0.47.0 可以在**同一轮**继续读取已经留存的下一段，不必重新请求网页，避免前后两段来自两个版本。继续读需要系统给出的有效位置；原留存缺失或字节不再匹配时，不会重新抓当前网页来冒充旧证据。这不等于界面已有逐条可点、精确定位的网页引用列表，也不是在线 PDF 阅读器。

## 重新打开时，问的是「当时保存了什么」

答复出现后，从历史重新打开原会话。要比较的是同一轮原问题和原正文，而不是再提交一次，等模型生成相似说法。在线自由问答可能只有已保存的正文，不一定有单独的 Markdown 报告；只有报告确实生成并保存了，才有报告可以下载。

v0.47.0 分开了**正文是否已确认保存**和**任务是否正常收尾**。正文已经保存，后来发生取消或收尾故障，原正文仍可读取，但任务状态不能因此改成「完成」。反过来，进度里出现文字也不代表已经保存。如果一轮明确要求报告，正文可读仍不能冒充报告已生成。服务端可以定点读一条已保存正文，不依赖其他历史条目是否可读；这不等于当前界面多了一个新的逐条恢复按钮。

稳定版、预发和正式运行环境也要分开看。本文命令使用 GitHub 上固定的稳定版；预发用来提前验证，正式环境要在部署后单独检查。把自己的工作台放到服务器时，按[从零部署篇](https://hpoenixf.com/eff-agent-article/articles/open-etf-agent-staged-deployment)配置认证和网络入口，不要直接暴露本地端口。升级后先检查原会话、原正文和原报告还能不能打开，不需要重新付费提问来代替这项检查。

下次想核对一份研究，先问一句：**我是要查新证据，还是要找回上次用过的证据和原来的回答？** 前者才需要发起新研究，后者应该先读历史。技术细节见 [v0.47.0 的实现与验证](https://github.com/hpoenixf/open-etf-agent/blob/v0.47.0/docs/verification/v047-retained-web-and-answer-delivery.md)。
