# Checkpoint 系统设计：Agent 保存什么，又凭什么继续？

一个研究任务读完两份资料，完成一次计算，保存了第一段报告，接下来准备核对第三份文件。此时关掉页面、重启服务、收到用户停止指令，会发生三件不同的事。

要把它们处理清楚，系统既要记得研究走到了哪里，也要认得哪些事情已经发生。检查点（checkpoint）参与前一项工作，但后者往往还依赖工具回执、报告版本、授权、请求记录和执行租约。

**一个好用的检查点系统，应该让正常研究容易接着做，也让中断后的系统能够准确判断哪些材料可以复用、哪些动作还需要重新获得执行资格。** 它不需要把整个应用变成一张永远可重放的图。

本文沿一个教学研究任务讲完整路径，再回看我们在 ETF Agent 中引入并移除 LangGraph 的经过。项目实践来自私有系统的设计与受控验证；文末另给公开教学仓库的可运行切面，两者的能力范围分别说明。

## 一、先看正常运行：一份检查点怎样产生

下面用一个合成任务贯穿全文：“比较两只基金的公开披露，计算持仓重叠，先交初稿，再补齐缺失资料。”示例中的资料和结果用于解释机制，不代表一项真实投资研究结论。

### 1. 接纳任务，取得本次执行身份

运行时（Runtime）先确认这次研究属于哪个账户、哪个任务、允许使用什么资料，以及可使用的资源。持久层为这次运行（Run）保留身份；当前执行者取得带围栏编号的租约。

租约说明谁暂时可以操作这次运行。围栏编号用来阻止旧执行者在接管之后继续写入。它们与模型是否记得任务、页面是否仍然打开，是不同的问题。

### 2. 记录模型提议，再执行获准动作

模型提出读取某份文件，宿主（Host）将提议绑定到本次请求与工具调用身份，再由工具执行路径核对权限、参数和预算。读取结束以后，原动作负责人保存结果与完成回执。

这个顺序很重要。检查点中的“下一步准备读取文件”只是一条进度线索；工具回执中的“该调用已经完成”才是一次动作的持久事实。恢复时不能只看进度线索就决定再读一次，更不能靠摘要猜测外部请求是否已经执行。

### 3. 保存接续位置与必要工作状态

运行时把下一阶段、当前工作状态和必要引用交给检查点保存接口。一个简化的快照可以包含：

- 属于哪次运行、采用哪个格式版本、这是第几次保存；
- 下一步进入模型思考、动作处理还是完成判断；
- 后续研究仍需要的观察、缺口和工作便笺；
- 指向原动作回执、资料身份与已保存结果的引用。

这些内容不必全部复制一遍。原回执已经完整保存的观察，可以在严格匹配身份与内容的条件下只留引用。无法从原记录准确恢复的内容，则必须保留在相应持久对象中。

### 4. 下一步消费，而不是再次创造事实

保存成功后，运行时按自己的生命周期继续。需要旧资料时，沿原结果引用读取；需要写报告时，交给发布系统保存正文和发布回执；需要等待用户或 Child 时，控制系统建立对应的等待关系。

需要真正读回检查点时，也不只是对一段 JSON 做反序列化。系统先核对这份快照所属的运行、格式和版本，再解析接续位置；被省略的观察只能从匹配的原回执补回，资料和发布结果仍沿原身份读取。工作状态整理好之后，还要由本次接续的负责人确认执行资格，才进入相应阶段。

这样，检查点保存的是一份可解释的交接材料，而不是某个进程的全部内存。格式不兼容、引用失配或原结果不可用时，读回方会得到具体的不可用结果，不能悄悄用空对象、摘要或新调用冒充原状态。

## 二、检查点旁边，还有哪些不能混在一起的记录？

研究系统里的几个“保存”，看起来都在写数据库，含义却不同。

| 对象 | 主要回答的问题 | 谁负责解释 |
| --- | --- | --- |
| 执行检查点 | 下一步在哪里，哪些工作状态可以接着用？ | 检查点与恢复边界 |
| 动作、模型请求回执 | 调用是否派发，结果已知还是未知，是否已经结算？ | 原执行与效果负责人 |
| 发布正文及版本 | 用户现在能读取哪一版成果？ | 发布系统与其读取接口 |
| 控制等待及唤醒 | 哪个回复或事件允许接回哪一个安全点？ | 原控制负责人 |
| 会话历史与长期记忆 | 用户说过什么，哪些信息适合下一次任务使用？ | 会话与记忆系统 |
| 研究工作区进度 | 长期研究做完什么，还缺什么材料？ | 研究工作区 |

最后一项也可能被命名为“checkpoint”。它描述的是研究目标和阶段成果，不是执行器的续跑游标。命名相同不意味着应该合并成同一个模块。

可以把执行检查点理解成一张工作交接单。交接单能指向已完成的计算和已保存的报告，却不能替代这些原件。它记录“下一步检查基金 B”，也不会自动给下一位执行者开通读取基金 B 私人资料的权限。

## 三、一次中断之后，系统实际要走哪条路？

**页面断开。** 服务进程与原任务仍然有效时，研究可以继续。页面重新打开，读取原正文和进度即可，无须为了恢复显示再调用模型。

**服务进程中断。** 先判断是否仍有有效执行者，再由原恢复边界核对围栏、已提交成果和未确认请求。ETF Agent 当前允许普通中断丢失有限的未提交进度，不默认在新进程中重建原主任务（Root）、子任务（Child）和等待关系。原任务按实际成果结算，用户明确继续时，再进入有自身准入的新 Run。

**合法控制唤醒。** 一次获准的人工回复或 Child 通知，可以在原等待、安全点、当前支持格式和执行身份都匹配时，接续它被允许的工作。这里既需要可用检查点，也需要原控制负责人接受的唤醒；只找到一条旧数据库记录还不够。

**用户要求停止。** 停止请求先由原控制通道接纳，再由当前执行接缝采纳。取消记录与运行收尾有自己的负责人，检查点保存失败不能把真实的取消改写成成功续跑；已经提交的报告和已经确认的工具效果也不会因此回滚。尚未确认的外部效果，仍按原请求事实处理。

这四条路径共同保留已经发生的事实，但对“是否继续原执行”的承诺不同。设计时先选产品需要哪种承诺，再决定检查点要保存多少状态，比默认追求所有步骤无损恢复更有效。

## 四、我们为什么用过 LangGraph，后来又移除了它？

2026 年 9 月，ETF Agent 从固定语义链迁移到持续研究 Runtime。任务不再只是按预设步骤走一遍，而是要不断读取、判断、调用工具、补充材料，直到可以交付。

当时采用薄 LangGraph.js StateGraph 是合理的：用三个逻辑阶段表达循环，接入持久 checkpointer，同时保留已有模型网关、工具与业务存储。图负责执行位置，业务系统负责工具和发布回执。我们没有要求框架接管整个产品。

随着系统发展，恢复所需的关键事实逐渐由应用自己的 Recovery 保存：模型轮次与提议、工具回执、正文提交、预算、租约、围栏，以及接续游标。图检查点则刻意只保存有界投影，完整的活动对象仍在当前进程中。

这时出现了一个具体问题：**新进程要安全接续，仍然必须先依赖 Recovery；图检查点自己并不能完成这件事。** 维护者却要同时理解图的 thread、cursor 和应用的运行身份、回执与续跑位置。

10 月初，我们移除了这层已经重复的图执行与 checkpointer 接线。三个逻辑阶段继续保留，变成 ResearchRuntime 内部的普通控制循环；持久接续仍由原 Recovery 提供。我们也没有再创建一个名字不同、职责相同的通用流程管理器。

这次选择的依据是当时项目的职责迁移，而不是“图框架不适合 Agent”。如果应用真正需要图分支、并行 super-step、状态分叉和时间旅行，而且愿意让框架承担相应的执行模型，LangGraph 仍然提供了完整而有价值的能力。

### 与 LangGraph 放在同一张地图上

[LangGraph 的检查点文档](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)以 super-step 为保存边界，记录线程的图状态，并支持中断后接续、时间旅行和已完成节点的 pending writes。我们这里保留的检查点围绕自有 Runtime 的受限接续协议组织。

| 比较维度 | LangGraph 提供的方式 | ETF Agent 当前选择 |
| --- | --- | --- |
| 执行组织 | 采用图 API 时，以图和 super-step 组织执行 | Runtime 内部三阶段循环 |
| 检查点内容 | 线程中的图状态快照及执行相关信息 | 接续位置、必要工作状态和原事实引用 |
| 状态存储 | checkpointer 对接相应状态存储 | 原 Recovery 合同下的内存（进程内）或 PostgreSQL（持久）适配器 |
| 恢复承诺 | 在框架支持的图边界恢复或分叉 | 普通中断有限结算；合法控制唤醒保留受限接续 |
| 外部效果 | 应用仍需处理幂等与结果未知 | 原请求、动作和发布负责人保存并解释回执 |

外部效果这一行尤其值得注意。LangGraph 的[容错文档](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance#retry-boundaries-and-idempotency)同样区分图检查点与节点内部的外部写入，要求稳定幂等身份，并把丢失确认视为未知。我们的回执设计与它解决的是同一类问题，不应把这部分写成框架没有考虑过的独创发现。

记忆也要单独看。LangGraph 区分线程内 checkpointer 与跨线程 Store；ETF Agent 的会话历史、长期记忆和恢复记录各有既有负责人。移除本项目的 LangGraph 接线，没有因此删除用户记忆。[官方持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## 五、检查点失败时，先确定失败发生在哪里

回到开头的任务。第一段报告已经提交，下一份检查点却失败了。至少要区分下面三种情况。

### 已知写前失败

例如状态中出现循环引用，JSON 序列化在进入数据库事务前就失败。此时可以确定：这份新检查点没有写入，上一份检查点没有被这次操作替换。

如果正文已由发布系统取得真实提交回执，快照失败不能让这段正文变成未发布。另一项独立读取能否继续，则仍看它自己的授权、预算、持久要求和当前租约。不能从“正文已经保存”推导后面所有动作都可随意执行。

我们在原执行接缝的受控验证中，分别检查了已完成读取、推理强度调整、已提交正文和取消请求后的这类失败。共同原则是让辅助快照错误停留在它自己的范围，但每种效果是否已经成立，仍由原负责人提供证据。

### 写入结果未知

数据库可能已经提交，客户端却没收到确认。这里不能报告“肯定没写”，也不能把异常当作一次安全重试的许可。需要沿原身份读取和核对持久事实；无法确认时，就保留未知状态。

同样的原则适用于外部模型或工具：未收到响应不代表没有执行，更不代表没有消耗额度。

### 租约、身份或必要安全点失效

如果当前执行者已经失去写入资格，即使快照本身完全能序列化，也不能继续使用旧围栏操作任务。若某次人工等待必须绑定一份精确快照，而这份快照不可用，系统可以拒绝建立那个等待或恢复动作。

拒绝一个依赖条件不足的操作，是相应模块的职责。是否结束整次研究、是否还能交付已有正文，则交回原运行和发布负责人判断。

### 容量治理也经历过变化

我们曾经遇到检查点重复携带大量已保存观察，触及应用设置的字节上限。先前的修复通过精确回执引用移除重复内容，同时保持原容量限制。后续又移除了人为固定的检查点字节上限，继续保留 JSON 可序列化检查与真实存储错误。

这两个阶段不要合并成“压缩以后永远不会超限”。去重减少重复表示，物理数据库和宿主仍有容量；模型上下文窗口也是另一套约束，不能用检查点能保存来证明请求一定装得下。

## 六、检查点应该有独立 owner，但边界要画在哪里？

这里的 owner，指负责解释某类事实并维护其不变量的模块，不要求独立进程、独立数据库或一个新的管理器类。

检查点模块有足够明确的工作：保存哪种格式、怎样核对身份与版本、哪些字段可以按原回执恢复、一次写入究竟成功还是未知、读出的快照是否适用于这次受限接续。这些规则值得集中维护。

但它不应该因为接触了运行状态，就接管运行的所有决定。

一个适合评审的分界是：

- **检查点负责人**可以回答“这份快照没有保存”“身份不匹配”“本次读取不可用”，并拒绝对应的保存或读取。
- **恢复与控制负责人**判断哪次唤醒和安全点可以使用这份快照，不能仅凭快照存在就开始执行。
- **动作、发布和取消负责人**分别确认自己的效果。快照不能撤销这些独立事实，也不能替它们补造成功回执。
- **运行负责人**综合仍然合法的路径，决定继续、收尾或停止。

这也解释了为什么单纯新增 `CheckpointManager` 不一定改善架构。如果它开始检查报告质量、核定预算、接管 Child、决定所有异常后的终态，我们只是给旧复杂度换了一个名称。

## 七、把重复判断收敛成什么样的模块？

现有实现已经分出检查点合同、编码校验、内存与 PostgreSQL 存储，以及生产恢复适配器。此前，不同调用点还要反复辨认“这是已知写前序列化失败，还是其他存储错误”；辨认之后，各自再判断本步能否继续。

这一轮收敛在 Recovery 内加入了一个独立保存模块。它只接收既有存储的检查点保存能力与原输入，统一解释两个能够确定的事实：

| 保存结果 | 模块返回什么 | 调用者还需要决定什么 |
| --- | --- | --- |
| 原存储已返回保存回执 | 已保存，以及原检查点回执 | 按原流程消费这份快照 |
| 已确认在写入前发生序列化拒绝 | 未保存，以及原类型错误 | 本步是否已有足够独立事实，允许不依赖新快照继续 |

其他错误继续沿原失败路径传播，保留原错误身份。模块不会把租约失效、权限失败、事务异常或丢失确认统一包装成一个容易被忽略的“可选失败”。尤其是写入结果未知时，它不会声称旧状态肯定没变。

普通快照、Main 上下文压缩后的快照、接续游标这三个现有保存入口都接到同一个接口。真正的格式校验、版本约束、事务写入与围栏仍由原存储合同承担，读回协议也没有被复制一套。这个保存模块本身不持有会话、预算、正文或控制等待，不负责重试、续租或决定终态。

**重复的错误分类被收敛，业务上的继续条件没有被抹平。** 已确认发布之后的辅助快照、必须绑定精确快照的等待、模型调用前的游标，各自需要不同的证明。原本依赖独立已提交控制回执而允许继续的特殊路径，也保留原负责人的处理；通用分类器不能反过来把它变成整轮失败。

这比增加一个“忽略错误”开关更有用：调用者拿到明确事实，再按照自己负责的效果处理。检查点可以有独立接口，同时留在原 Recovery 的存储和权限边界之内。

上述接口与三个调用入口的迁移已合入当前实现，完成不调用真实模型的本地离线验证与独立审查，覆盖原恢复、终态和等待接缝。本轮没有改写底层存储事务，也没有扩展普通中断后的恢复承诺；这些工程结果不代表真实模型、生产数据库或部署已经验收。本次远端 CI 未通过，返回信息未说明失败原因，也不能记成远端流水线成功。

原有初始检查点路径虽然已有窄范围处理，其单独验收仍未完成；其他独立检查点工作也没有因这次接口收敛自动完成。模块边界变清楚了，不等于原系统的每一种恢复场景都已验证。

## 八、用公开教学代码观察两个关键出口

私有系统的完整恢复协议不是开源教学版的能力清单。想亲手观察“结果已提交”和“外部结果未知”的差别，可以使用 [Open ETF Agent 的固定公开快照](https://github.com/hpoenixf/open-etf-agent/tree/5f70dc0b4760ad70ef211f4823828ab2fee5c525)。这是 v0.7 开发阶段的教学实现，不是把本文全部设计打包成了库。

在 Node.js `>=26.8.1 <27` 环境中：

```bash
git clone https://github.com/hpoenixf/open-etf-agent.git
cd open-etf-agent
git checkout 5f70dc0b4760ad70ef211f4823828ab2fee5c525
npm ci
node --test --test-concurrency=1 --test-name-pattern='after result commit|dispatched-without-result' test/durable-runtime.test.mjs
```

[对应用例](https://github.com/hpoenixf/open-etf-agent/blob/5f70dc0b4760ad70ef211f4823828ab2fee5c525/test/durable-runtime.test.mjs)使用脚本化模型与测试拥有的子进程，实际在边界处终止进程，再由另一个进程打开原状态。一个出口消费已有结果回执，不重复原工具效果；另一个出口保留 `TOOL_OUTCOME_UNKNOWN`，不把未知调用重发。

观察重点是调用次数、原回执和最终状态，而不是模型生成了多少文字。这些用例不用真实模型调用；本次写作核对了固定源码，没有重新执行它们。当前项目入口见 [Open ETF Agent](https://github.com/hpoenixf/open-etf-agent)，新版本行为应按相应版本说明阅读。

## 结语：从下一次交接出发设计检查点

回到那份尚未完成的基金比较：第一段报告由发布系统保留，已完成计算沿原结果回读，第三份资料是否继续获取由当前执行资格决定。检查点把这些工作线索组织成可接续的状态，但不替任何负责人重写事实。

下一次设计检查点时，先回答三个问题：**谁会读这份状态，读完以后要做什么，哪些事实必须回到原记录确认？** 再决定保存边界、格式与失败处理。这样得到的模块既有独立职责，也能留在整个研究系统正确的位置上。
