# Tool、Function Calling、MCP、Skill，一次行动怎样发生？

<LearningPathNav />

你准备给助手增加“读取产品指南”的能力。搜索一圈，会同时看到 Tool、Function Calling、MCP、Skill。每个介绍都能举出读取文档的例子，究竟应该从哪里开始？

可以先跟踪一次具体行动。用户要求比较 Atlas Notes 两版指南，助手需要取得 A 版第一页。这是我们公开示例中的合成资料。先看取得这一页需要哪些东西，再把名称放回对应位置。

## 先有一项实际能力

应用需要一段真正能够取得页面的程序。教学上，可以写成一个普通函数。

```javascript
async function readPage({ documentId, page }) {
  return documentStore.readPage(documentId, page)
}
```

这里的 `documentStore` 是解释用的占位对象。函数可以读取本地文件，也可以访问远端文档服务。

当应用把这项能力提供给模型使用时，还需要说明名称、用途、参数和结果。模型据此选择，应用负责检查并执行。我们把这种受控、可调用的能力称为工具（Tool）。

同一项底层能力可以被多个界面使用。用户点击“打开页面”时调用它，自动化脚本也可以直接调用它。Agent 增加的选择过程，是让模型结合当前任务提出下一步请求。

## 模型怎样把请求交给程序

如果模型只输出“我准备读取 A”，应用还得猜该调用什么。Function Calling（函数调用）或 Tool Calling 提供结构化表达，让模型指定工具名和参数。

下面是简化后的内部提案，字段用于说明关系。

```json
{
  "name": "read_page",
  "arguments": {
    "documentId": "atlas-a",
    "page": 1
  }
}
```

供应商协议可能给这份请求添加调用 ID、内容块和流式事件。适配层把它转换为应用可以理解的对象，再交给工具宿主处理。工具结果随后与原调用配对，进入下一次模型输入。

**模型提出请求，应用完成动作。** 参数是否合格、文档是否属于本次允许范围、是否还有预算，以及最后是否真的取得内容，都需要实际执行链路回答。函数调用格式本身无法证明读取成功。[Anthropic 工具使用说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

工具回答“能做什么”，函数调用回答“怎样表达这次请求”。从一个进程内函数开始，就能建立这条关系。

## 能力在另一个程序里时，MCP 怎样接入

如果文档由一个独立服务维护，应用需要知道它提供哪些能力、每项能力接收什么参数，以及怎样取回结果。MCP（Model Context Protocol）为宿主与服务之间的连接提供了标准化方式。

在工具这条路径上，客户端可以发现服务提供的工具，再发起调用。MCP 还定义了资源与提示等其他能力，具体宿主可以选择支持哪些部分。[MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

一次读取可以经过下面几次交接。

```text
MCP 客户端发现 read_page
→ 应用把允许使用的工具说明交给模型
→ 模型提出结构化调用
→ 工具宿主通过 MCP 客户端请求页面
→ 服务返回内容
→ 应用把结果交给下一轮模型
```

模型供应商的函数调用协议与 MCP 连接分别服务不同的接缝。应用可以用前者接收模型请求，再通过后者取得外部能力。模型也可以调用应用内的本地工具，全程无需 MCP。

采用 MCP 的价值通常出现在独立服务接入、标准客户端复用和多种宿主共享能力时。一个只在当前进程里使用的小函数，直接注册往往更简单。

## 有了工具，为什么还会需要 Skill

现在助手可以读取两版指南，但仍可能比较错口径。A 版第一页提到免费版与企业版，B 版也有对应条件。仅拥有读取能力，并不能自动形成良好的比较方法。

Skill（技能包）可以提供任务方法、说明和相关资源。一个比较指南的 Skill 可以提醒助手读取相同物理页、保留版本与版本内的适用条件，并分开比较免费版和企业版。[Agent Skills 格式说明](https://agentskills.io/specification)

Open ETF Agent 的公开比较 Skill 正好采用这类方法说明。它告诉助手怎样使用资料，宿主仍负责实际能力与执行边界。[固定比较 Skill](https://github.com/hpoenixf/open-etf-agent/blob/bcc12995c83abfbd5b37b9792f5a86ab74aa788e/fixtures/skills/compare/SKILL.md)

不同宿主对 Skill 的资源加载、脚本执行和工具声明支持各有范围。Skill 目录中存在脚本，能说明包提供了资源，执行能力还取决于宿主的实现和本次授权。

一份好方法也可能完全使用本地工具。MCP 服务可以在没有 Skill 的情况下供普通程序调用。选择哪一种，应回到当前缺少的是方法、接入方式，还是实际能力。

## 用同一次任务对照四个概念

| 概念 | 在文档比较中承担什么 | 应当观察什么 |
| --- | --- | --- |
| Tool | 提供读取页面、保存报告等实际动作 | 调用的参数、结果与实际产物 |
| Function Calling | 表达模型选择的工具与参数 | 请求是否完整，结果是否配对 |
| MCP | 连接外部文档服务及其工具 | 服务发现、调用和返回是否接通 |
| Skill | 提供比较方法及相关材料 | 方法是否被加载，并影响了后续工作 |

应用把它们接在一起，才可能形成一次有方法、有能力、有结果的行动。给工具换个描述无法修复断开的服务，安装服务也不会自动补齐比较方法。

## 在公开示例中看完整过程

按[上一站的 v0.26.0 安装步骤](./prompt-context-rag-memory.md#在-open-etf-agent-中观察一次)准备项目后，运行下面的例子。

```bash
npm run demo -- --case skill-mcp
```

它按需读取比较 Skill，通过实际启动的标准输入输出 MCP 示例进程取得合成页面，最后保存报告。终端返回本次目录，其中的 `report.md` 可以检查比较内容，`run.jsonl` 可以查看行动记录。

本次示例采用预设模型动作，MCP 示例进程也使用合成文档。它让读者观察真实的程序连接与结果交接，模型能否自行选择正确方法仍需另外检验。[固定 MCP 实现](https://github.com/hpoenixf/open-etf-agent/blob/bcc12995c83abfbd5b37b9792f5a86ab74aa788e/src/mcp.mjs) · [当前项目入口](https://github.com/hpoenixf/open-etf-agent)

运行时可以特别留意三个问题。方法在什么时候读入，真正的页面通过哪个工具取得，报告的保存有没有实际回执。这三个观察点，能帮助你把四个名词连接到具体行为。

## 下次增加能力时，先确定缺少哪一部分

需要一个简单动作时，先实现并注册工具。需要让模型明确表达调用时，接上工具调用协议。能力由另一个服务提供时，评估 MCP 接入。相同类型任务反复需要同一套方法时，再整理为 Skill。

每增加一种机制，都需要维护对应的描述、连接或资源。采用条件明确，读者就能从最小方案开始，随着实际需要逐步扩展。
