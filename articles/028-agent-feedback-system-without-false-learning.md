# 做了评测、日志和护栏，为什么 Agent 仍可能越改越偏？

> 内容主线：**系统架构与工程观点**；兼线：AI 工程研发实践。本文讨论纠偏系统怎样产生错误反馈，不重写评测体系、Langfuse 或 Publication 的组件教程。

我们起初以为，给 Agent 加上评测、追踪和发布护栏，工程师就能告别“凭感觉调 Prompt”：失败有红灯、调用有日志、违规输出有拒绝原因。系统只要不断吸收这些错误，就会越改越可靠。

实际工作给了我们一个更麻烦的答案：**反馈本身也可能是错的。**

有时红灯来自评审模型没有生成完整 JSON，而不是被测 Agent 没完成任务；有时 Trace 少了一轮，只是记录时把超大正文丢了；有时最终历史里没有新版答案，模型却早就提交了完整修订。若把这三件事都算成“模型回答能力不足”，下一步修改就会朝错误方向走。

所以我们后来更在意的，不是如何把反馈闭环做得更密，而是：**每次反馈有没有资格推动对应层的修改？**

## 一、第一个错觉：评测器报错，不等于被测模型报错

在早期质量评估里，一类严格 JSON 评分结果经常无法解析。仪表板上表现为失败，很容易被直接归入“本轮质量评估没有通过”。

但继续拆分请求后，我们发现其中一部分发生在评审模型自身：输出预算不足以让它完整生成格式要求很严格的评分对象。调整评审端的输出额度和请求合同，可以消除相应的格式失败，却不会自动让原待评答案更有用。

有些被测回答依然太短，没有覆盖用户问题。它们应该继续被判为内容不足，而不是随着评测器 JSON 能解析，就一并成为高质量样本。

这里的变化不在于“多加一个 Judge”，而是我们把同一盏红灯拆成两类：

| 看起来一样的失败 | 真正应该修改的位置 |
| --- | --- |
| 评审响应被截断，结构不完整 | 评测器自身的预算、格式协议和失败归因 |
| 评审正常完成，发现研究缺证据或答非所问 | 被测 Agent 的实际研究与输出路径 |

如果评价系统没有这层区分，团队会把**修好尺子**记成**被量的东西变好了**。下一轮还可能因评分程序换了版本、分母变了，却拿前后的通过率直接比较。

我们开始要求每个结论至少保留当时的任务输入、候选版本、评审执行身份、成功或缺失的具体对象。跨窗口比较前，先确认比较的是同一件事。

## 二、第二个错觉：日志看不到，不等于运行没有发生

后来我们用 Langfuse 追踪研究过程，最初只希望看见工具调用和模型请求。直到一次长研究的诊断，我们发现应用端的模型正文捕获有一条 256 KiB 边界。

序列化内容超过 262144 字节时，正文可能被拒绝采集。更糟的是，在输入输出双侧都没有正文的情况下，某些历史读取投影连整个模型回合都可能漏掉，而分页又显示已经读完。

这时，如果有人统计“Agent 实际用了几轮模型”或“这次是否真正调用过某项工具”，只看追踪列表就可能得出错误分母。

正确修复不是无限扩大记录容量。那会增加存储、隐私和维护成本，也只是把问题推迟到更大输入出现时。

我们保留正文上限，同时为**已知因为容量限制而丢失的正文**留下有界的缺失事实：准确的调用身份、输入还是输出缺失、已经知道的原因。合法的 JSON null 和根本没采集到正文，也必须分清。

这样，追踪系统终于能够说“调用发生了，但正文没留下”，而不是悄悄让那轮从统计中消失。

但历史上没有缺失回执的旧记录，仍然只能保持 unknown。不能因为今天补上了机制，就替昨天编出一个确定的原因。

这是我们第一次意识到：**日志不是执行的替身，日志缺失本身也要成为有范围的观察事实。**

## 三、第三个错觉：没有持久答案，不等于模型没写好

最典型的一次归因错误发生在回答质量验收中。

我们一直在改善渐进式回答，希望模型别把几段研究过程机械拼成一篇报告。某次真实复验结束后，Recovery 读取的仍是旧正文。沿着结果看，似乎模型没有完成最后的文章修订。

如果就此修改 Prompt，我们很可能要求模型生成更多总结、增加收尾提示或延长修订过程。

可是把不同来源的回执按身份放到一起，情况完全变了：

模型实际上已经提交了完整新版；发送工具接受了 replaces 提议；预览也显示新文章。旧内容保留在 Recovery，是 Factory 的非标准发布路径只协调了 commit，没有完成 replace 持久化。

这不是模型写作失败，而是**已接受的修订与数据库的最终效果不一致**。

修复沿已有 Recovery 归属读取原块的 scope、run、ID、revision 和展示位置，交给原有的版本、撤权和提交检查。确定性回归里，新版本成为实际持久正文，并能够进入下一次组装的模型请求。

随后我们撤回了原来的“模型不会写最终答案”归因，也撤回了先前不能成立的写作质量改善因果判断。

这里最值得积累的不是又一次代码修复，而是一次**主动撤回错误解释**：当更强的执行证据出现，旧诊断必须让位。

## 四、三次经历暴露了一个共同的系统问题

我们原本把评测、追踪、发布看作三道越来越严密的保护。现在更愿意把它们看成三个**可能互相验证，也可能互相矛盾**的观察者。

评测器负责判断目标样本在既定标准下表现怎样，但它自己可能失败。

遥测系统提供请求和调用的诊断视角，但它自己可能漏采、裁剪或异步发送失败。

持久运行与发布回执保存执行效果，但某一次读取路径也可能使用错误的版本关系。

没有任何一方只凭自己的“成功/失败”字段，就有资格解释整次用户任务。

我们现在做复杂问题定位，会先问：

**红灯对应的是被测对象还是裁判？Trace 为空是没调用还是没采到？正文没出现是模型没写、Publication 没接受，还是已接受效果没有持久提交？**

这些不是换三种说法重复“模型不可靠”。它们分别要求检查不同的事实归属，因而决定了完全不同的修复动作。

## 五、可靠的反馈闭环，反而必须允许“不知道”

这里很容易走向另一个极端：既然每个环节都可能有漏洞，那就再加一层检查器，把所有不确定性都拦住。

但不受控的阻断本身也会产生错误：某条公开引用不能验证，可能只需要降级这个附件；如果因此拒绝整篇本来获准的解释，用户实际得到的答案反而更少。

我们最终希望保留三种纠偏结果：

**确实定位了缺陷。** 可以把根因指向某个拥有事实的模块，做最小修复，再以正反回归证明对应机制变化。

**原来量错或看错了。** 修复评价器或观测链，同时撤回原有错误归因；不把红灯减少说成模型质量提高。

**证据仍不足。** 保留 unknown，补最关键的那次可观察交接；没有必要为了制造闭环而再发一轮模型、再加一个状态机。

这也解释了为什么我们不把“评测、护栏、留痕”本身宣称为金融 Alpha。它们可能减少可避免的错误和错误归因，但尚未直接证明研究判断更准、更快或投资收益更高。

工程团队真正应该复用的，是一句不太响亮、却能节省很多弯路的话：

**只有证明反馈来自哪里，才能决定下一步应该改变什么。**
