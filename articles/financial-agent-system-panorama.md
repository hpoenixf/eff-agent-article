# 金融 Agent 全景：连接研究、业务与责任的系统架构

金融 Agent 可以读财报、比较基金、解释组合风险。接入模型和工具之后，更重要的问题是：哪些事情可以让它自主完成，哪些必须由程序和业务系统管住？

**我们的选择是：给研究足够的空间，把数据权限、重要计算和真实操作管好。** 不让模型凭一句话改动账户，也不因为一份资料没读到，就让用户什么都看不到。

下面用“两只基金是否买重了”这个教学例子，说明六个设计选择。ETF Agent 当前的对话研究层不直接交易；文中的下单情节用于说明未来接入业务系统时需要分清的责任。

## 一、先分清：用户是在问问题，还是要求动账户？

用户在同一个聊天框里说出的话，可能是三种完全不同的任务。

| 用户说什么 | Agent 要完成什么 | 需要管住什么 |
| --- | --- | --- |
| “这两只基金有什么区别？” | 查资料，解释投资范围、费用和风险 | 资料来源与使用范围 |
| “结合我的持仓，看看是不是买重了。” | 读取获准持仓，分析重复暴露 | 只能使用获准账户的数据 |
| “按这个方案替我买入。” | 将明确的操作请求交给业务系统处理 | 账户、产品、金额、授权与实际执行结果 |

前两种任务可以让 Agent 自主补查、比较和计算。第三种涉及真实资金，不能沿用“允许查资料”的权限直接下单。个性化建议是否属于产品获准提供的服务，也需要单独确认，不能只看有没有交易按钮。

在系统里，研究工具默认只读；真正的操作通过独立业务接口完成。权限和限额由程序检查，不靠提示词提醒模型“请勿越权”。用户说“照做”，也要对应明确的方案、账户和金额，不能让模型自行补齐。

业务系统没有返回明确结果时，应先查询核对，不能为了完成任务再下一单。模型说“买好了”，不等于账户真的成交了。

**研究可以自主推进，操作只能在明确授权内发生。**

## 二、重要数字交给工具，但先把“算什么”说清楚

比较两只基金的重叠，不能只数它们共同持有几家公司，还要看每家公司占了多少，以及用户在两只基金里分别投了多少。

沿用这个教学例子：基金 A 占组合的 40%，B 占 20%；公司 X 在两只基金中的权重分别为 8% 和 12%。假设两份披露的时期、分母和统计范围可比，那么：

**40% × 8% + 20% × 12% = 5.6%**

这个计算适合交给代码，模型负责解释。但 5.6% 的含义只能是：按这些输入，两只基金中已观察到的公司 X 持仓，对组合合计贡献了 5.6% 的暴露。组合里的其他资产、未披露持仓，可能还有额外暴露。

如果 A 用的是半年前的持仓，B 用的是最近披露，或者一个权重按基金净资产计算，另一个按股票资产计算，就不能不加处理地相加。首先要补齐可比数据；补不到时，可以展示各自的已知情况，说明为什么暂不合并。

收益、费用和回撤也一样。计算之前，先弄清楚对象、日期、单位和方法；计算之后，保留输入与结果，方便复算。

**Python 能按公式运算，却不会替我们证明输入和方法选对了。** 给模型更多计算工具，还要让它知道什么时候用、结果该怎样解释。

## 三、引用要让人查得回去，不是给答案贴一张“正确”标签

一份报告有很多引用，当然比只说“根据公开资料”更方便核查。但链接是真的，不代表结论就成立。

比如，两只基金的前十大持仓有几家公司相同，可以说明“已披露的这部分存在重叠”，却不能直接说“整个组合高度重复”。结论比资料多走的那一步，仍需要判断。

对研究系统，更有用的设计是让用户点开引用后，看到当时实际读取的段落或表格，知道资料是哪一期；需要核对数字时，还能找到计算输入和方法。

报告保存后，也应能回到当时的依据。网页后来更新了，不能拿新页面冒充旧报告使用的材料；原材料确实无法取得时，就说明缺口，而不是用摘要重新拼一份“原文”。

保存这些记录，是为了回答“这个结论从哪里来”。不需要把所有内部细节摆在正文里，更不能把客户持仓和敏感原文不加区分地塞进普通日志。

## 四、资料不全，先交付能说明白的部分

假设基金 A 的资料读到了，基金 B 的完整持仓暂时拿不到。此时有两种很差的回答：一种编出完整重叠率；另一种只说“信息不足，无法分析”。

更有用的回答可以是：

> 已查到基金 A 的持仓与行业分布，可以先说明它的集中情况。基金 B 的完整持仓还缺失，暂时不能计算两只基金的完整重叠率；已取得的 B 基金资料仍可用于比较投资范围和费用。

用户拿到了目前可用的信息，也知道下一步缺什么。数据缺失，没有被包装成“没有风险”；部分缺口，也没有抹掉已经做好的研究。

我们在发布治理中做过一个重要调整：**把局部问题留在局部处理。** 引用显示有问题，修引用；一个指标缺输入，标明该指标暂不可算；后面的工具调用失败，保留前面已经交付的内容。

这不包括泄露未授权资料。未经授权的客户数据及依赖它的内容，仍然不能因为“先交付一点”而被放出来。

判断尺度很简单：这是缺少分析材料，还是根本没有使用权限？前者可以限制结论、保留其他成果；后者必须限制相应的数据使用和披露。

## 五、多 Agent 和人工复核，要用在真正需要判断的地方

查管理费，没有必要叫齐多头、空头和裁判。比较一项投资假设，才可能值得增加不同视角。

例如，用户认为“再买一只科技基金可以分散风险”。支持者可以检查新增产品是否带来不同资产；质疑者可以核对底层持仓是否仍然重叠、近期用钱需求是否被忽略。真正有价值的是找出：什么证据会让原来的理由不再成立？

多个 Agent 读着同一份不完整材料，即使意见一致，也不能补出缺失事实。因此，应先核对数据和计算，再把有争议的假设交给不同方法审视，不靠多数票决定答案是否正确。

人工复核也要分场景。普通研究不必默认等人逐条审批；真实业务中需要人审的操作，应按既定业务规则触发，不能由模型一句“我很有把握”来豁免。

复核提出问题后，可以补证、解释分歧或修订报告。它不应轻易变成另一个让整份研究消失的开关。

## 六、最后验收的，是用户真正拿到的研究结果

模型调用成功、脚本运行结束、报告文件生成，都只是中间步骤。回到开头的问题，用户最终需要知道：两只基金哪里重叠、目前能算到什么程度、这个发现是否改变了原来的配置理由。

一份有用的交付，至少应该让用户看懂主要结论、查到关键依据、看见重要缺口，并能打开和重新找到报告。不能只有工具调用记录，却没有回答问题；也不能显示“已生成文件”，点开却拿不到。

测试时也别只选资料齐全的顺利情况。可以故意让一只基金缺少完整披露、让两份数据的日期不同，或让一次补查失败，看看系统能否继续交付正确的部分，而不是编造或清空答案。

已有引用和计算能力后，下一步更值得检查的是：**模型有没有用对方法、读懂结果，并把它们变成用户需要的解释。** 这比继续增加一层通用审核，更接近实际研究质量。

## 从一项有用的研究开始

回到“两只基金是否买重了”：Agent 应该能查资料、调用计算、比较解释，并把已知和未知一起交给用户；它不应凭研究结论改写持仓，也不应为了等待完美证据一直没有答案。

底层可以使用现有 Agent 框架，不必先自建一整套金融平台。先选一个明确的问题，接好数据和计算，把报告交到用户手里，再根据真实缺陷补能力。需要接入业务操作时，再与原有账户、风控和订单系统划清职责。

**好的金融 Agent，要同时做到两件事：尽可能帮助用户完成研究，不替用户或业务系统做未经授权的操作。** 安全和可用性，都要落在这条具体任务路径上。
