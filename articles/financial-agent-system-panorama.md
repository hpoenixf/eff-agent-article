# 金融 Agent 全景：连接研究、业务与责任的系统架构

用户问：“我已经买了两只科技基金，再加一只，是增加分散，还是把同一种风险又买了一遍？”

一个能聊天的模型可以解释分散投资。一个能用工具的 Agent 可以查基金、读持仓、运行计算。但要真正帮用户回答这个问题，还需要把许多事情接起来：持仓属于谁，资料是哪一期，重叠怎样计算，结果意味着什么，缺了什么信息，以及最后交付哪份报告。

用户接着说“那就按你说的调整”，系统又面临另一类问题：研究结论是否足以构成操作请求？谁核验账户、产品和金额？没有收到交易结果时，该查询还是重试？

**金融 Agent 的全景，就在研究与业务之间：让模型灵活完成研究，让数据、计算、权限和真实操作各有明确的负责人。** 只强调自主性，会忽略行为后果；只强调限制，又可能让用户始终看不到有价值的结果。

本文用一个合成的基金组合案例，串起整套系统。ETF Agent 当前的对话研究层不直接交易；图文中的订单、结算和机构审批是接入业务系统时的目标分工，不是已经上线的交易能力。

## 一、金融场景为什么不能只换一套知识库？

不同场景的 Agent 都需要可靠性。金融研究的难点，不在于其他行业可以随便出错，而在于同一个问题经常同时包含**精确事实、开放判断和可能产生资金影响的动作**。

先看精确事实。基金名称相似，不代表份额相同；今天下载的报告，持仓可能仍属于上个季度；基金净值涨幅，也不一定等于投资者实际获得的回报。单个数字可以完全真实，放进错误的比较里仍会误导。

再看开放判断。“两只基金都持有公司 X”是事实，“这个组合太集中”则需要结合权重、其他资产和投资目标。程序可以计算集中度，却不能只凭一个指标替所有用户决定是否应该调整。

最后是行为后果。解释费用、读取私人持仓、给出情景比较、提交真实订单，看起来都发生在同一个聊天框里，实际需要的权限和责任并不相同。

| 用户的请求 | 研究应推进到哪里 | 不能悄悄发生什么 |
| --- | --- | --- |
| “这几只基金有什么区别？” | 比较公开或获准的产品资料 | 把不同时点、份额或口径当成同一事实 |
| “结合我的持仓，看看有没有买重。” | 使用获准持仓，分析已知暴露与缺口 | 用聊天记忆冒充当前账户数据 |
| “比较维持、减少和继续投入。” | 在产品允许的服务范围内做条件化分析 | 把模拟结果当成已执行的配置 |
| “按这个方案办理。” | 进入独立的业务确认、授权与执行流程 | 因为模型已经研究过，就直接取得操作权限 |

因此，第一项设计工作不是选模型，而是明确产品提供哪种服务。个性化建议是否属于获准业务，也不能只看有没有交易按钮。这里讨论技术分工；具体业务资格与审查要求仍由相应机构按适用规则确认。

关于研究、建议与交易的进一步区别，见[《当 AI 开始谈“买什么”，研究助手离投顾和交易还有多远？》](030-fintech-from-research-to-investment-advice.md)。

## 二、先看整张地图：谁保管事实，谁负责研究？

可以把系统想成一个研究团队，但不要把每项职责都理解成一个 Agent。账户系统保管持仓，数据工具取得资料，模型组织分析，计算程序处理明确的方法，交付系统保存报告。这些角色协作，却不互相取代。

![金融 Agent 的四类职责：投资记录、数据入口、研究交付和运行观察；业务操作另行授权](../visuals/financial-agent-system-panorama/reader-system.svg)

[放大查看系统分工图](../visuals/financial-agent-system-panorama/reader-system.svg)

**投资记录回答“用户实际上有什么”。** 份额、现金、已确认记录，应从负责这些事实的原系统读取。Agent 可以解释它们，不能因为自己生成了一份新摘要，就改写原账户。个人投资记录也不能被包装成券商成交回报。

**数据入口回答“这次取得了什么”。** 网页、PDF、行情接口和内部知识库各有用途。入口应保留来源、数据时点、读取范围和失败原因，把材料准确交给研究者。它不应在统一格式的过程中，擅自决定“这些资料不够专业，所以整个问题不能回答”。

**研究与交付回答“怎样把材料变成有用结果”。** 主 Agent 理解问题、选择方法、调用工具，必要时分派子任务。算出的结果、形成的解释和交付的报告需要接在一起，而不是各自完成就算结束。

**运行观察回答“哪里发生了什么”。** 工具为什么失败，模型有没有看到结果，正文是否保存，用户是否拿到文件，这些需要可核对的记录。观察系统负责帮助排查，不负责替用户选基金，也不因为掌握日志就获得访问全部私人材料的权限。

这里划分的是职责，不是要求部署四个微服务。小系统可以把它们放在同一个应用里。真正需要避免的是让模型同时充当研究员、账户记录维护者和交易批准者，或者让某个数据适配器变成隐藏的研究裁判。

底层框架可以承担模型调用、工具编排和状态管理；金融业务系统继续负责自己的账户、规则和操作。两边通过接口协作，不必为了接入 Agent 重建一套账本。

进一步的权责设计见[《模型会理解，代码才授权》](011-model-understands-code-authorizes.md)；多源接入的取舍见[《一个金融数据 MCP，为什么长成了研究决策系统》](mcp-market-responsibility-retrospective.md)。

## 三、一项研究怎样推进：不是固定流水线，而是带反馈的循环

回到“再买一只科技基金是否更分散”。用户给的是一句话，系统需要完成的却是一组相关判断：已有资产是什么，新基金增加了什么，哪些风险没有变化，哪些条件会改变结论。

![研究循环：明确问题、取得材料、比较和计算、交付解释；发现重要缺口时补查，也可先交付独立成立的部分](../visuals/financial-agent-system-panorama/reader-loop.svg)

[放大查看研究循环图](../visuals/financial-agent-system-panorama/reader-loop.svg)

### 先形成能推进的问题，而不是先填满一张表

如果用户只想知道三只基金的投资范围，公开资料就可以推进。只有到了“对我的组合有什么影响”，才需要读取获准持仓；缺少新增金额时，可以先说明定性差异，不必让整个研究停在澄清页面。

关键是区分两类信息：**缺了就会改变本次判断的条件，和可以边研究边补充的细节。** 例如近期要取出一笔钱，会直接影响情景比较；一个暂时不影响主要结论的辅助指标，不该成为开始研究的前置条件。

### 取得材料后，还要决定它能回答什么

读取结果可能是一份完整持仓，也可能只有前十大；可能是基金净值，也可能是交易价格。研究者需要据此调整问题，而不是让每份材料都去回答同一个预设模板。

发现两只基金披露时期不同，可以寻找可比期间；发现只能取得部分持仓，可以先分析已披露部分，并保留未覆盖范围。补查的目标是解决具体缺口，不是把工具列表全部调用一次。

### 计算以后，研究还没有结束

工具可以返回共同持仓、行业分布、费用或风险情景，但用户问的是“是否更分散”。主 Agent 仍需判断这些结果与原问题的关系：新增产品带来的是不同名称、不同公司，还是不同的风险来源？当前材料足以支持到哪一步？

如果结果暴露出新问题，研究可以回头补查。如果继续搜索收益很小，或本次资源已经不足，则应交付现有成果、说明未决项，而不是无限循环，也不是把“没有继续查”写成“已经没有问题”。

这种循环里，模型决定研究路线，程序管理获准工具、运行资源和真实记录。**灵活性放在“下一步研究什么”，确定性放在“能做什么、实际做了什么”。**

更完整的任务推进机制见[模型与研究循环的协作机制](etf-agent-model-harness-research-loop.md)。

## 四、数据、计算、判断：三者接得上，报告才有深度

把算术交给 Python 是必要能力之一，但研究质量不能只看“是否调用过计算工具”。更有用的检查顺序是：输入描述了什么，方法适不适用，输出又被怎样解释。

### 数据先带上对象、时点和口径

假设基金 A 占组合的 40%，B 占 20%；公司 X 在两只基金中的权重分别为 8% 和 12%。在披露时期、分母和统计范围可比的教学条件下：

**40% × 8% + 20% × 12% = 5.6%**

这个结果说明，按这些输入，A、B 两只基金中已观察到的公司 X 持仓，对组合贡献了合计 5.6% 的暴露。它不是“两只基金的整体重叠率”，也不是公司 X 在整个组合中的最终暴露：其他资产或未披露部分可能还有贡献。

如果其中一个权重按基金净资产计算，另一个按股票资产计算，就不能直接相加。若披露时期不同，也应保留日期，选择可比材料或明确说明比较限制。今天读取到的资料，并不会因此成为今天的持仓。

### 方法需要明确，结果需要保留含义

费用估算、历史收益、持仓穿透和风险情景，是不同的问题。费用还可能涉及条款和舍入，收益需要说明是否包含分红，情景分析则要说明假设。程序负责按照明确方法计算，研究者负责选择方法并理解它适用的条件。

我们已有的计算实践将单位、方法、输入与局部限制跟随结果传递，目的就是避免一个正确数字在转述时变成另一个意思。一个指标不能计算，不应让其他有效结果一起消失；一个近似结果可以有用，但不能在报告里丢掉它的近似条件。

### 份额与持有期：费率规则会改变研究结论

假设用户问：「同一只基金的 A、C 份额，如果打算持有一年半，哪种总成本更低？」不能只套用「A 适合长期、C 适合短期」的经验。研究需要先识别基金及份额代码、申购渠道与折扣、申购金额、预计持有期、赎回费和持续费用，再让确定性工具按同一金额与期限复算。

这一案例还存在真实的时间变化：中国证监会在 2025 年 12 月 31 日公布修订后的[《公开募集证券投资基金销售费用管理规定》](https://www.csrc.gov.cn/csrc/c101954/c7606091/content.shtml)，自 2026 年 1 月 1 日施行，明确对持有超过一年的非货币市场基金份额不再收取销售服务费。已有基金的费用结构与法律文件存在过渡调整安排，具体判断仍须核对适用日期的基金合同、招募说明书及销售渠道条款，不能把监管原则直接当成某只基金的即时报价。

缺少份额身份、有效费率或交易确认日期时，Agent 应标出缺口并取得资料，而不是猜一个比例。资料齐全后，程序计算，模型解释费用比较在哪些条件下成立。这里没有给出指定基金的真实费率，因此不能声称 A 或 C 必然更便宜。金融知识在这一步真正改变了计算方法与结论资格，而不只是增加一个时间标签。

### 分红与披露：正确的数字也可能回答错问题

基金分红后单位净值通常相应下降，但现金分红、红利再投资会改变持有人现金或基金份额的构成；仅比较除息前后单位净值，不能表示投资者实际回报。可以依据含分红的适用业绩口径或持有人份额与现金流复算。基金业协会的[投资者教育资料](https://investor.amac.org.cn/community/tzzhdzthd/ylj/202307/t20230706_14858.html)对这一点作了说明。

同理，两份基金报告若只披露了前十大持仓，计算结果就只能说明**已披露持仓的共同暴露**，不能写成全持仓重叠率；披露期不一致，则应寻找可比材料或限定结论。相比单纯展示 5.6% 的算术，说明这个数值代表什么、还有什么没有覆盖，才是金融研究的关键。

### 多来源用于解决差异，不用于凑数量

两家供应商的收益率不一致，先检查份额、日期、币种和收益口径。确认是同一问题后，再判断是否存在数据错误或修订。两个相同数字也可能来自同一份转载，不能只因链接数量翻倍就视作独立验证。

没有必要规定每个事实必须找两份来源。关键数据要能核查；存在重要冲突时，要把冲突及其对结论的影响说明白。研究成本应该花在能改变判断的地方。

计算机制分别见[《金融 AI 最危险的“专业感”：数据是真的，数字却算错了》](031-fintech-data-time-and-reproducible-numbers.md)和[《Agent 明明调用了 Python，为什么投研报告还是会算错？》](financial-agent-python-result-consumption.md)。

## 五、多 Agent 与人工复核：增加不同问题，不是增加相同声音

单个 Agent 可以完成简单研究。任务复杂后，多 Agent 的价值主要来自两种分工：一种处理材料，例如分别阅读两份长报告；另一种检验假设，例如分别研究“新增产品带来分散”与“新增产品只是重复暴露”。

前者提高任务组织能力，后者帮助发现遗漏。两者都需要把所用材料、方法与未解决的问题交回主 Agent，不能只交一句“建议买入”。否则，主 Agent 获得的是一个更自信的结论，而不是更扎实的依据。

在我们的例子中，支持新增的一方可以寻找不同的行业或公司暴露；质疑的一方可以检查持仓重合、资金安排与极端情景。最终应讨论的是**哪条证据成立、哪项条件改变后需要改判**，而不是数一数几位专家赞成。

如果大家使用同一份不完整材料，多几个角色也不会补齐事实。查管理费或解释一个定义，通常没有必要增加一轮多方讨论。额外协作有时间和费用成本，应看它是否真的带来了新的检查角度。

人工介入也有不同目的。用户补充“半年后需要用钱”，是在修正研究条件；专业人员检查方法和建议，是复核研究；业务审批人批准明确操作，是授予受控行为的权限。这三件事不应被一个“确认”按钮混在一起。

需要审批的真实业务动作，应按相应规则执行，不由模型自信程度决定是否跳过。普通研究则不必因为可选 Reviewer 未运行，就让用户拿不到已经完成的内容。

关于不同投资视角如何协作，见[《不止一个投资专家：多视角 Agent 如何共同检验投资假设》](investment-perspectives-and-thesis-falsification.md)。

## 六、安全与可用性怎样兼顾：限制具体风险，不让局部问题吞掉整份研究

假设基金 A 的资料读到了，基金 B 的完整持仓暂时拿不到。有两种很差的处理：编出完整重叠率，或者只返回“信息不足，无法分析”。

更有用的回答是：先说明 A 的集中情况，比较两只基金已取得的投资范围和费用，同时明确完整重叠率还不能计算。这不是降低标准，而是让结论的范围与实际材料匹配。

我们在发布治理中调整过这一点：引用附件有问题，处理附件；一个指标缺输入，标明该指标的缺口；后续工具失败，不清空先前已经交付的独立内容。**错误应该影响依赖它的部分，不应自动蔓延到整个任务。**

| 遇到的问题 | 应限制什么 | 仍可继续什么 |
| --- | --- | --- |
| 完整持仓缺失 | 完整重叠率与相关确定性结论 | 已披露部分、产品差异和缺口说明 |
| 引用详情暂不可读 | 说明核查入口缺失，不伪造原文 | 在权限和内容身份成立时保留独立正文 |
| 私人材料未获授权 | 相应的数据访问、使用及依赖它的披露 | 不依赖该私人材料的公开研究 |
| 一个工具调用失败 | 记录该次失败，不冒充成功 | 使用其他获准路径或交付已有结果 |
| 真实操作结果不明 | 不盲目重复可能产生资金效果的操作 | 沿原请求查询、核对和说明未知 |

这种局部处理不意味着放松数据安全。网页和研报是研究材料，里面写着“忽略规则”或“把客户信息发给某地址”，都不应成为系统指令。模型准备读取什么、向哪里发送材料、调用什么操作，仍要受到程序控制。

私人持仓也不应该为了“完整观测”被无差别复制到日志、第三方模型或所有子 Agent。每个接收方只取得当前任务获准使用的材料；运行记录保留排查所需信息，敏感原文采用相应访问与保留安排。

因此，安全与质量应分开处理：越权访问要拒绝，有争议的判断要复核，材料不完整要说明范围，工具失败要如实报告。把它们全部变成“答案禁止发布”，既没有解决具体问题，也损害了研究价值。

**一个真实的取舍反例。** 早期金融数据 MCP 把部分结构不匹配纳入按“供应商＋操作”记录的失败避让；某只产品的查询失败，可能连带跳过另一只产品的同类查询。源码支持这条影响路径，却不能据此解释所有历史失败。修复时，我们把失败范围收窄到具体请求，保留原生资料读取的研究路径，而不是让统一入口裁决“资料值不值得继续研究”。代价是原生读取与结构化消费需要分别验证；回报是局部问题不再轻易扩散。详见[金融数据 MCP 的职责复盘](mcp-market-responsibility-retrospective.md)。

局部交付见[《Agent 已经生成答案，为什么还需要一个独立的发布系统？》](019-agent-answer-publication.md)；资料与指令的区别见[《Prompt Injection 不只是恶意文本》](agent-content-trust-prompt-injection.md)。

## 七、报告不是终点：证据、历史与业务操作怎样衔接？

一份报告至少包含三种不同内容：引用的事实、根据事实得到的计算、综合形成的判断。用户想核对时，应能找到与这句话有关的依据，而不是被迫阅读整段运行日志。

![研究成果与业务动作分开：原资料、计算和报告可关联核查；用户另行提出操作后，由业务系统核验、执行并记录实际回报](../visuals/financial-agent-system-panorama/reader-handoff.svg)

[放大查看研究与业务衔接图](../visuals/financial-agent-system-panorama/reader-handoff.svg)

### 证据要跟得上结论，交付要跟得上生成

对 5.6% 这个数字，核查入口应说明用了哪两份持仓、用户组合权重是什么、公式怎样计算，以及覆盖限制是什么。对“继续买入未必更分散”这个判断，还要说明它依据哪些事实、增加了什么假设。

保存这些关系，是为了重建当时的依据和实际行为，不是为了声称已经记录模型全部内部思考，也不保证重新运行时能生成逐字相同的报告。引用提供核查入口，结论是否成立仍需判断。

与此同时，生成、保存和交到用户手里是不同的事。页面已经显示部分正文，后续保存可能失败；服务端有了文件，用户可能仍打不开。界面应保留能看到的内容，同时如实说明保存或下载的问题，不能把“生成成功”替换成“用户已经收到”。

### 历史用于比较，不能悄悄变成当前事实

一个月后用户再问“现在呢”，旧报告有两种价值：保留当时的判断依据，帮助识别哪些条件发生了变化。它不能替代本次持仓、最新披露或新的用户约束。

持续研究应比较“原先基于什么判断、后来哪些事实改变了”，而不是把新资料覆盖进旧报告，造成当时就已知道后来信息的错觉。记忆可以帮助理解用户偏好，当前账户事实仍从原系统读取。

### 业务操作是另一条需要独立确认的路径

报告交付后，只读研究可以结束。用户明确提出操作请求，才进入另行定义的业务流程：核对准确方案与账户，在适用规则下检查权限、风险与必要批准，再由业务系统执行并依据实际回报更新记录。

“同意这个分析”“已提交订单”“已成交”不能当作同一状态。没有明确结果时，查询和对账比盲目重试重要。研究系统可以帮助解释进度，却不能用一段自然语言创造交易事实。

### 一个监管要求，怎样变成可检查的工程控制

对于适用中国内地证券基金规则的经营机构，[《证券基金经营机构信息技术管理办法》](https://www.csrc.gov.cn/csrc/c106256/c1653896/content.shtml)第四十三、四十四条规定，委托技术服务不免除机构责任，重要信息系统须保持机构控制，并预先考虑服务方更换；[《证券期货投资者适当性管理办法》](https://www.shfe.cn/regulation/futureslaw/202501/t20250114_824326.html)第二、三条明确相关销售或服务的适用范围与经营机构的适当性义务。是否适用，仍须结合服务主体、具体业务和地域判断。

这对应一项具体的架构决策：研究 Agent 可以生成“调整基金 B”的分析，但**模型结论或聊天确认不能代替业务批准**。若机构提供获准的申购或调整服务，应由原业务系统核对准确账户、产品、方案版本、适当性、权限及必要审批，并以实际执行回报更新记录；更换外部模型或工具服务方，也不应丢失这些事实及其关联。

**这是依据规则作出的工程映射，不是法规逐条规定了 Agent、审批模块或接口名称**，也不表示当前 ETF Agent 已接入机构交易流程。

证据传递见[《金融 Agent 的可信证据链》](financial-agent-trustworthy-evidence-chain.md)；持续研究见[《Investment Thesis：周报后的跨期研究》](agent-weekly-thesis-history-continuous-research.md)。

基金申赎还有独立的时间事实：申请交易、确认基金份额与赎回款到账不是同一个事件。通常交易确认在 T+1，部分特殊基金可能 T+2 或更晚，持有时间应依基金合同及实际确认记录判断，不能直接以申请日计算短持有期费用。深圳证监局的[持有时间说明](https://www.csrc.gov.cn/shenzhen/c105614/c7602071/content.shtml)给出了实例。本文说明的是业务建模方法，不代表 ETF Agent 已接入实际申赎或结算。

## 八、怎样判断系统变好了：不只看答案，也不只看工具调用

把功能逐项接通以后，最容易出现的错觉是：来源可查、Python 跑过、报告保存了，所以研究已经完成。真正的验收仍要回到用户原来的问题。

对“新基金能否增加分散”，列出三只基金的资料还不够。报告需要说明比较了什么、哪些暴露改变了、哪些风险无法据此判断，以及什么条件会让结论变化。不能用一篇篇幅很长、引用很多的报告替代这个回答。

我会把评估分成四个视角，而不是生成一个总分，让它决定整篇内容能不能显示。

| 评估视角 | 具体检查什么 | 不能拿什么替代 |
| --- | --- | --- |
| 运行与交付 | 工具、结果、保存、下载和历史回读是否接通 | 模型接口返回成功 |
| 金融研究 | 对象、时点、方法、数字和解释是否适用 | 调用过 Python 或引用数量多 |
| 用户价值 | 是否回答原问题，用户还要补做多少工作 | 正文字数和 Agent 数量 |
| 安全与成本 | 是否越权，额外补查与复核是否值得 | 拒绝越多越安全、运行越久越深入 |

测试既需要资料齐全的正常题，也需要关键反例：两份披露时期不同、只取得部分持仓、某次计算失败、保存中断。希望看到的不是全部任务都被拒绝，而是系统能保住可用成果，不捏造缺失部分。

发现错误后，还要沿着原路径定位：是数据没取到，公式不对，模型没采用计算结果，还是最后解释错了？修数据读取、修算法和修模型指导，针对的是不同问题。不能每次都靠增加 Reviewer，也不能因为答案错了就断言底层工具失效。

新的模型、提示词或方法上线前，复用这些真实问题进行比较；结果不佳和未能交付的尝试也要留下。这样积累的是能够指导下一次改进的案例，而不是只保留顺利演示的材料。

引用与研究质量的区别见[《为什么 AI 明明有很多引用，回答还是不够可靠？》](ai-citations-do-not-prove-reliability.md)。

## 九、落地顺序：先做好一项研究，再扩大能产生的业务效果

全景图不是采购清单。团队不需要先建完记忆、多 Agent、审计平台和交易系统，才开始验证产品价值。更合理的起点，是选一个资料可取得、方法可解释、成果可核对的研究任务。

第一阶段可以聚焦只读研究：接好必要来源和计算，让用户拿到报告，并能追问、核对与重开。第二阶段再进入员工协作：处理岗位权限、复核意见、版本修改和交接。真正需要执行业务时，才进一步接入账户、产品、风险、审批、订单和回报系统。

这种顺序按后果扩大能力，而不是按模型数量扩大架构。前两阶段可以独立创造价值；接了交易接口，也不意味着第三阶段已经具备完整条件。

对现有 ETF Agent，更值得继续投入的是让已有引用、计算、协作与交付在真实研究题中稳定配合。工程机制已经存在，不等于每份金融报告都正确；这个差距需要通过真实问题、可复算结果和用户使用来缩小，而不是继续把所有环节变成强制门禁。

从全景回到开头那句话：用户不是来参观我们的组件，而是想知道是否买重了。系统应尽可能完成这项研究，交代已知与未知，并守住数据使用和真实操作的界限。

**全景架构的价值，是让数据能进入研究、计算能支撑判断、判断能形成成果，成果又不会未经授权变成业务操作。** 这几段交接清楚了，既可以保留 Agent 的探索能力，也能让金融业务知道责任落在哪里。
