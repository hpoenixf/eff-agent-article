# Agent Engineering Suite：让 Agent 从需求一路接到发布

> 本文基于 [Agent Engineering Suite 的固定公开版本](https://github.com/hpoenixf/agent-engineering-suite/tree/3b515de2f30e25b1e0757243f3ce4d1be19b00b0)。后台报告功能是合成教学案例，用于说明工作方式；下文的安装结论来自实际受控验证。

Agent 写出一段代码之后，研发工作并没有结束。接下来还有几个更难回答的问题：它解决的是不是原来的问题？为什么采用这个设计？异常路径有没有验证？换一个会话之后，下一位执行者能不能继续？

我们把项目中使用的需求追问、Spec 流程、架构深化、代码审查、History、文档维护和成熟度评估整合到同一个仓库：[Agent Engineering Suite](https://github.com/hpoenixf/agent-engineering-suite)。已经独立公开的 Spec 与 History 工具也是本次整合的来源，而不是另起两套实现。它们各自有用，但放在一起的价值，应该体现在一次任务怎样交接，而不是插件数量。

**这套工具要保留下来的，是问题、决定和证据之间的联系。** 代码可以继续改，计划也可以调整，但下一步不能只靠 Agent 记得上一轮说过什么。

## 1. 从一个小功能开始，看见真正的工作量

假设我们要给一个应用增加“后台生成报告”的能力：用户提交任务后可以离开页面，回来查看进度，也可以取消任务。

这个例子看起来很适合直接交给 Agent 实现。加一个接口，接一个任务队列，再做一个进度组件，似乎就够了。但只要继续问几句，设计就会分叉：

- 用户关闭页面，任务应该继续还是停止？
- 点击取消时，已经生成的报告要不要保留？
- 服务重启后，是接着执行，还是重新生成？
- 同一任务被重复投递，会不会产生两份结果？
- 用户只能看到自己的任务，这个限制由哪里保证？

这些答案会改变实现，不能等代码完成后再靠修补决定。套件的第一个入口，就是把这种分叉提前暴露出来。

### 先追问决定，再写 Spec

Grilling 的作用是沿着设计分支追问，而不是把所有常识都变成问卷。仓库里已有的约定，应当先读；不影响决策的细节，可以合理推导；真正改变权限、交付语义或者成本的选择，才需要明确下来。

在这个例子里，可以先确定一个范围：关闭页面不取消任务；主动取消阻止后续生成；已完成报告仍可读取；恢复不能绕过当前访问权限。

随后由 Spec 流程把这些决定变成可检查的行为。Spec 不必重复所有讨论，却必须留下目标、非目标、关键场景和完成条件。比如“页面关闭后仍能完成”与“服务崩溃后能够恢复”是两个不同的承诺，不能用一个“支持后台运行”笼统覆盖。

这一步交给实现者的，应该是一份能判定对错的约定，而不是一段听起来正确的需求摘要。

这部分已有独立公开基础：原 OpenSpec Evidence Kit 提供 Spec 检查与证据视图相关工具，现已纳入公开套件。它检查记录与约定的结构，不能替人证明一次真实执行已经发生。统一套件保留了这条边界，没有把一个检查命令包装成自动验收。

## 2. 架构深化与代码审查，分别解决什么问题

有了 Spec，仍然不应该马上新增一个“统一任务管理器”。先看现有代码里谁拥有任务状态，谁负责持久化，谁判断结果可以对用户可见。

如果这几个职责已经有明确归属，新增模块就应该复用它们。否则，一个简单功能很容易带出第二套任务状态、第二份权限检查和第二条发布路径。表面上每个模块都很小，整体却越来越难理解。

架构深化关注这类边界：能否让接口更简单，让完整的业务责任收敛到合适的模块内部？哪些转发层没有承担真实职责？哪些重复状态应该消失？它不以新增抽象的数量衡量进步，也不要求每个项目都长成同一种架构。

代码审查则针对一批具体变更，回答另两个问题：它是否符合工程要求，以及它是否实现了约定的行为。

回到报告任务：实现可能很整洁，却在恢复路径忘记检查用户权限；也可能覆盖了功能，却把状态转换分散到三个调用方。前一种更靠近需求合同缺口，后一种是结构问题。把两类判断区分开，才能给出可以执行的修复意见，而不是泛泛地说“建议优化”。

两者可以相互触发，但不应该互相冒充。小修复不必先做全仓重构；架构问题也不会因为这次 diff 没有明显错误就自动消失。

## 3. 验收要沿着用户路径走，而不是停在代码通过检查

后台报告的正常路径很容易演示：提交任务，等待完成，点击下载。真正决定能否采用的，往往是另一条路径：任务执行到一半时服务退出，恢复后用户取消，而旧执行者又返回了结果。

在这个合成场景中，需要检查的是：

1. 取消状态是否阻止旧结果被当成新成功发布。
2. 恢复是否沿用正确的任务身份，而不是悄悄新建一次执行。
3. 报告读取是否仍然受当前权限约束。
4. 重复请求是否产生重复交付。

这些检查可以先用合成数据和受控故障完成。它们有明确价值，但如果实际功能还依赖外部模型或服务，就需要另外完成对应集成的验收。测试里的模拟返回不能替代真实服务已经接通，模型返回了文本也不能证明用户已经拿到了文件。

因此，首版的 Workflow 入口提供验收、发布和交接模板，帮助把“实现了什么”“在哪种环境验证”“还差哪个条件”记录清楚，并绑定到被检查的代码版本。这些模板没有另造测试执行器或自动发布编排器，执行与接受变更仍由项目已有流程负责，也不会因为执行者说了完成就自动归档。

证据可以很小。对这个例子，一份说明输入条件、操作、可观察结果和对应版本的记录，比一长串通过数量更有帮助。下一次修复改变了恢复逻辑，也应当知道哪些旧结论需要重新验证。

## 4. History 留下决定，文档帮助使用

做完功能之后，最容易丢掉的是“为什么”。几周后有人看到取消逻辑里保留已完成文件，可能认为这是残留数据，顺手删除；另一位执行者看到恢复前再次检查权限，可能认为前面已经检查过，可以合并。

History 应当留下当时的约束、被放弃的方案、改变判断的证据以及剩余问题。它不需要保存每一次工具输出，也不应把私人数据、原始日志或临时密钥变成项目知识。

保存决策理由并不是一个新发明。[架构决策记录（ADR）](https://adr.github.io/)已经明确强调选择背后的理由、取舍与后果。这里希望进一步解决的是 Agent 工作中的衔接：后来的执行者既能找到决定，也能看出它对应哪个版本、是否已经被后续决定替代。

原 Engineering History Skill 的初始化、候选记录、校验和快照工具，以及手工维护区域保护，也已进入公开套件。不过，一份候选材料是否值得成为长期历史，仍然需要判断。工具可以守住记录边界，不能自动赋予材料重要性；它也不会自动访问私人 Agent 对话或替用户总结所有经历。

使用文档承担另一项职责。用户要知道怎样提交、取消、查看报告，以及升级时有哪些限制；贡献者要知道状态归属和修改入口。没有必要让他们先阅读全部设计历史。

所以文档同步与清理要同时做两件事：把当前行为写到正确入口，把过期或重复的说明标记、迁移或者删除。清理前必须检查引用、当前用途和可恢复性。历史验收依据仍在使用时，不能仅凭文件很旧就认定它没有价值。

最终留下的应当是能够继续使用的知识，而不是越来越大的日志仓库。

## 5. 打分器和 Roadmap 为什么要拆开

项目成熟度评分回答的是“当前能力站在哪里”。Roadmap 回答的是“下一步为什么做这件事，以及怎样才算做完”。

对后台报告功能，评分可能发现：权限隔离已有证据，重启恢复已验证，但真实服务的失败处理还不足。Roadmap 再据此安排下一项工作，写明负责人、依赖、阻碍和验收条件。

两者值得共享证据，却不应该共享一个简单的完成开关。

例如，总体分数提高了，不代表报告任务的恢复问题已经解决；某项能力分数下降，也可能只是评价范围扩大、发现了过去没有覆盖的情形。直接把分数映射成进度百分比，会让计划显得精确，却掩盖真实剩余工作。

这也是把 Roadmap 做成独立模块的原因。它维护稳定的事项身份，允许候选想法经过评估、进入 Spec、实现、验证和验收；被否决或暂缓的事项也保留理由。评分提供观察，路线图负责把观察转成可追踪的选择，完成仍以该事项的验收条件为准。

共享证据并不要求再建一个大型平台。初期用版本化、可审阅的仓库文件就可以连接这些模块，避免为了追踪研发，又先开发一套新的研发管理系统。

公开成熟度模块只提供通用评价标准、确定性计算工具和合成示例，不携带私有项目路径、职责映射或当前基线。使用者需要提供自己的评价和证据；公开量表使用独立身份，不与私有历史量表直接比较。算术正确不代表评价正确。Roadmap 当前提供独立工作方法和事项模板，没有声称已经实现项目专用的状态验证器或自动关闭流程。

## 6. 一个仓库，两种使用方式

统一仓库维护一份核心内容，通过构建脚本生成 Skill 与 Codex 插件两种形态。目前模块划分为 Spec Flow、History、Grilling、架构深化、代码审查、文档维护、成熟度评估、Roadmap 和可选 Workflow 入口。前面案例中的环节由这些模块分担，验收与发布模板属于 Workflow，并非额外实现了一套运行平台。

旧 Spec 和 History 仓库的来源、提交历史和发布元数据保存在[迁移记录](https://github.com/hpoenixf/agent-engineering-suite/tree/3b515de2f30e25b1e0757243f3ce4d1be19b00b0/docs/legacy)中，既有中英文文章也使用统一入口。保留的旧版本用于追溯与恢复，不是另一份要继续维护的现行实现。

- **独立 Skill**：适合已经有自己的工作流，只想补一个环节的人。例如只采用架构深化，或者只接入 History。
- **Codex 插件**：把模块所需的入口、说明与相关资源按宿主格式打包，减少手工组织成本。

每个模块都有单独包，也提供完整套件包，均由同一份源内容生成。完整安装带来的是选择上的方便，不意味着每次任务必须启动全部模块。修复一个拼写错误，不需要先做需求访谈和成熟度评分。

这项整理没有把现有插件目录直接拼起来。有些原组件依赖特定平台的工具；有些带着 ETF 项目的路径、指标和发布习惯。通用版把项目配置与工作方法分开：核心规定怎样识别证据、怎样交接和检查，项目配置提供目录、命令、领域指标及授权边界。例如文档维护改为本地适配与精确清理计划，没有假装移植了原先专属的 ChatGPT GitHub 集成，也不自动永久删除文件。

只安装 Roadmap，不需要被迫接受 ETF 项目的评分表；选择独立 Skill，也不需要暗中安装整个插件集合。安装器会先给出计划，默认不修改目标；已存在的同名 Skill 不直接覆盖，更新与移除需要核对安装记录和文件内容。它还检查已知范围内的重叠安装，但无法保证发现另一个远端宿主或未知缓存中的冲突。

在 Linux 的 Codex CLI 0.163.0 上，已从上述固定公开提交完成真实 Git marketplace 获取，并分别验证单个 History 插件和整套插件的安装、列表读取、全部安装文件字节比对与移除。它证明的是这条安装路径，不代表模型任务质量、其他平台兼容性或公开插件商店审批。

如果希望先使用 History，可以沿已验证的固定版本安装：

```bash
codex plugin marketplace add https://github.com/hpoenixf/agent-engineering-suite.git --ref 3b515de2f30e25b1e0757243f3ce4d1be19b00b0
codex plugin add agent-engineering-suite-history@agent-engineering-suite
```

完整套件改用 `codex plugin add agent-engineering-suite@agent-engineering-suite`，不要与已安装的单模块重叠。独立 Skill 的计划预览、更新与移除见[安装说明](https://github.com/hpoenixf/agent-engineering-suite/blob/3b515de2f30e25b1e0757243f3ce4d1be19b00b0/docs/installation.md)；它们与插件来自同一核心，但使用不同安装机制。当前持续维护入口在[仓库首页](https://github.com/hpoenixf/agent-engineering-suite)。

## 7. 套件应该主动，但权限不能随之扩大

研发工具越能连续工作，越需要明确它在哪些地方停下来。

读取代码、提出修改、执行本地验证、写入仓库、推送远端和公开发布，是不同操作。Skill 中的一句“持续推进”不应该自动获得全部权限。外部模型调用也应当遵循项目已有的数据范围和费用限制，而不是以验收为名自行开启付费服务。

清理模块同样如此：它可以识别冗余并准备可审阅的清单，但不能把无法判断用途的文件当成垃圾。备份存在也需要核对覆盖范围，不能用一个本地提交号承诺所有工作已经安全。

来源许可是另一条边界。这些工作方法中包含对既有开源实践的适配。公开时需要保留上游归属与许可证，确认可再分发范围；私人插件可以使用，不等于其中所有来源材料都能一并公开。无法确认权利的部分，应当先排除或独立重写。

套件的可信度，既来自它帮助完成了什么，也来自它能够准确说明哪些事没有完成、哪些操作没有获准。

## 8. 从你最容易断开的地方开始

不必为了使用套件，先把现有研发流程全部替换掉。

如果需求经常做到一半才发现理解不同，可以先接入 Grilling 和 Spec 流程；如果代码持续膨胀、一个改动需要触及许多模块，可以先做架构深化，再让审查检查具体变更；如果任务换一个会话就难以继续，先把 History 与交接整理好；如果总觉得事情很多却不知道下一步，使用成熟度评估识别缺口，再由 Roadmap 排序。

回到后台报告的例子，最终要交付的不只是一段能运行的代码，还包括清楚的行为约定、经过验证的恢复与取消路径、可供用户使用的说明，以及后续改进的依据。发布维护再检查这些入口是否指向同一版本，升级说明是否兑现了实际兼容边界。

创造能力让项目向前走，维护和升级能力让它走得更久。这套研发工具的整理目标，就是让每次前进都留下下一步能接得住的东西。先从一个真实任务验证这条链路，再逐步扩大使用范围，比一开始要求所有 Agent 执行一整套仪式更有意义。


完整 Spec 与 History 机制分别见[证据驱动的研发流程](/articles/026-agent-spec-evidence-workflow)与[工程知识维护](/articles/027-agent-context-document-history)。
