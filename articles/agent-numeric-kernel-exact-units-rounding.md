# 精确数字并不等于正确投资：单位、舍入与残差的数值核设计

一个基金研究 Agent 算出 **2.06 元**，可能完全符合算术规则，却不适合当作投资建议：份额来自昨天，净值来自今天；不同币种被相加；费用已经体现在净值里，却又扣了一次。

因此，金融 Agent 不需要一位“万能数学裁判”，而需要严格区分两类责任：**精确数值运算（Numeric）** 保证给定十进制数值、单位和舍入政策下的确定性结果；**确定性投资计算等领域模块** 选择公式、判断输入和分母是否适用，并决定业务结果的资格。本文围绕一条金额计算讲解 Numeric 的接口和实现边界。所有例子为合成输入；局部数值测试不代表金融研究质量已经获得认证。

## 一、输入必须保留计算以前的意义

**图 1：从原值到解释，数值核不应补造领域前提。**

~~~mermaid
flowchart TD
    A[来源数据与原始精度] --> B[领域 Owner 选择对象/时点/方法]
    B --> C{单位/尺度/运算绑定明确?}
    C -- 否 --> X[局部拒绝并标明原因]
    C -- 是 --> D[A33 精确数值运算]
    D --> E[返回 exact/rounded/residual]
    E --> F[领域 Owner 检查业务约束]
    F --> G[Result 保存身份和适用限制]
    G --> H[模型解释与原 Publication 交付]
~~~

二进制浮点不能准确表达所有十进制小数，超过安全整数范围时甚至可能在解析阶段丢掉原始数字。把普通 number 最后格式化为两位小数，不能修复计算前已经发生的精度损失。

因此，输入采用十进制**字符串**，且把舍入政策显式传入：

~~~json
{
  "quantity": { "value": "137", "unit": "CNY" },
  "factor": { "value": "0.015", "unit": "ratio" },
  "rounding": { "scale": 2, "mode": "half-toward-positive-infinity" }
}
~~~

这不是说 1.5% 是任何真实基金的合法费率；选择费率属于金融领域。

## 二、精度、单位、尺度与方法是四个问题

| 维度 | 示例 | 最终责任 |
| --- | --- | --- |
| 数值表示 | 2.055、1e-400 | Numeric 保留十进制精度与比较结果 |
| 单位 | CNY、USD、shares:fund-A | 来源/领域声明；Numeric 拒绝不兼容运算 |
| 比例尺度 | 0.25 ratio、25 percent | 领域按版本化合同显式换算，不按数值大小猜测 |
| 方法与分母 | 收益率、费用、份额估值 | 领域 Owner 选择，Numeric 不决策 |
| 结算/展示精度 | 两位小数、货币量子 | 领域指定政策，Numeric 执行 |

相同单位可以直接加减，CNY 与 USD 不应该被默认相加。份额乘同对象单位净值须由调用方声明维度：**shares:fund-A × CNY/share:fund-A → CNY**。Numeric 不推断基金对象，不查询实时汇率，也不保证来源数据新鲜。

百分点尤其容易出现尺度误判：0.02 decimal-difference 可按相应合同解释为 2 pp，但已经记录为 2 percentage-points 的源值不得再次乘 100。

## 三、舍入是一种规则，不是视觉格式化

137 × 0.015 = **2.055 CNY**。采用显式两位小数和已声明的 tie 政策：

~~~json
{
  "exact": { "value": "2.055", "unit": "CNY" },
  "rounded": { "value": "2.06", "unit": "CNY" },
  "roundingResidual": { "value": "0.005", "unit": "CNY" }
}
~~~

此处残差定义为 **rounded − exact**，所以是正 0.005；它不是“计算错了”。负数更能检验政策：既有精确数值核采用 half-toward-positive-infinity，负向半分边界 **−10.075 → −10.07**，不是 −10.08。它符合明确的 tie 规则，但不是所有金融产品统一使用的舍入方法。

实现并不需要先把它变成浮点：137 的整数系数是 137、尺度是 0；0.015 的系数是 15、尺度是 3。相乘得到系数 2055、尺度 3，即 2.055。结算到两位小数时，再按显式规则处理商和余数，最后把结算值与原精确值对齐尺度，算出残差。当前内核用 BigInt 系数做这些有限运算，跨 JSON 仍返回十进制字符串。

为什么负数的 tie 没换成更熟悉的“远离零”？这里延续的是原领域的 Math.round 方向，不是宣布一种普适金融规则。2026 年 10 月 20 日的原查询合成反例里，1000 × 0.189915 − 200 精确等于 −10.085 CNY，旧路径却产生 10.09 的卖出额，而该既定政策应为 10.08。修正先让乘法与减法保留十进制值，再执行同一政策，没有借修精度改变业务规则。这个新反例也不证明已还原更早缺少原始输入的研究失败。

先计算、按领域政策结算、最后格式化，与“每一步先四舍五入再继续”通常不等价。

## 四、精确比较不能被展示层吞掉

1.00 CNY 与 0.999 CNY 在两位小数界面中可能都显示为 1.00，但前者仍严格大于后者，精确差额是 **0.001**。非常小的正十进制数（如 1e-400）也不能因为转换成普通 number 而被判等于零。

这个差异真的会改变业务判断：原合成查询曾让预算或可用现金只有 0.999 的“买入 1 元”在分位展示后看似可行，也有 0.001 的保护储备缺口。当前领域先比较未舍入差额，再给出资金不足；显示成 1.00 不能反过来授权支出。

“现金不得为负”仍是领域规则；Numeric 只保证对选定同单位数值的比较。允许哪种容差、违反时应拒绝哪项交易假设，都由原业务 Owner 决定。

## 五、残差还可能揭示不可行约束

**图 2：不要用自然语言解释掩盖严格约束彼此冲突。**

~~~mermaid
flowchart TD
    A[领域指定目标和约束] --> B[A33 精确运算和比较]
    B --> C{守恒与约束都成立?}
    C -- 是 --> D[保留确定性结果]
    C -- 否 --> E[返回差额和受影响字段]
    E --> F{领域有合法容差或调整政策?}
    F -- 是 --> G[原领域局部调整后复算]
    F -- 否 --> H[报告不可行或缺条件]
    D --> I[模型解释不替代领域批准]
    G --> I
    H --> I
~~~

假设某个合成配置要求三个权重**严格**等于 0.333，同时总和**严格**等于 1。精确相加为 0.999，差额 0.001。这不是浮点误差，也不是把三个权重展示成 33.3% 就能解决。

由哪个资产桶吸收差额、是否允许现金权重变化、容差多大，必须由投资领域决定。Numeric 只返回可复算的值；严格约束相互矛盾时，应保留局部不可行结论，而不是生成看似守恒的组合。

两个对照案例也说明了相同问题：已知价格但未知持仓日期，乘法精确仍不代表当前估值合格；假设费用可复算不等于实际扣款已经发生，净值已包含费用时不能再次默认扣减。

## 六、整数分、十进制库，还是一个窄数值核？

**只处理固定结算单位时，整数最小货币单位往往更简单。** 例如 [Stripe 的金额接口](https://docs.stripe.com/currencies#minor-units-in-api-amounts)按币种最小单位接收金额，不能一律假定每种币都除以 100。若业务已经完成结算、只需要记账与支付，保留币种和整数金额就很合适。但上面的净值、费率和 0.001 缺口还在结算之前；过早只留“分”，就丢掉了判断所需信息。整数也要使用足够范围的表示，不能换个单位就忽略溢出。

**需要更多运算或舍入策略时，成熟十进制库更合适。** [decimal.js](https://mikemcl.github.io/decimal.js/)已有可配置精度、多种舍入方式及除法等运算；它也提供与这里 tie 方向对应的 ROUND_HALF_CEIL。仍须从原十进制字符串输入，并明确精度和业务政策。库不会自行识别基金身份、净值日期或币种，单位边界仍要由应用表达。

**这里选择的是需求已经明确的窄内核。** 当前消费者需要同单位加减与比较、显式绑定的乘法、比例缩放，以及 exact/rounded/residual 三个结果；用有界十进制解析和 BigInt 系数就能覆盖，不需要跨语言 RPC 或通用金融 DSL。代价是它只支持现有有限操作和一种显式舍入政策，不是完整 Decimal 替代品。需求扩到一般除法、更多政策或复杂函数时，应重新评估成熟库，而不是把这个小模块无限扩展。

协方差等统计方法仍可在声明样本和误差后使用浮点；精确金额不意味着所有数学都必须迁入同一引擎。职责按输入和业务语义分开：

| Module | 应当拥有 | 不应当拥有 |
| --- | --- | --- |
| 精确数值运算（Numeric） | 精确运算、单位匹配、舍入与残差 | 投资公式选择与来源认证 |
| 隔离分析 | 沙箱、输入绑定和真实脚本执行 | 执行成功即金融正确 |
| 确定性投资计算 | 金额、配置与领域约束 | 全局 Run / Publication 否决 |
| 研究结果与引用管理 | 结果身份、依赖和回读 | 重新计算原业务结果 |
| 正文发布与内容准备 | 正文版本和交付 | 统一金融语义裁判 |

这个边界还有迁移成本：已经在 number 入口丢失的原始数字，改成字符串也补不回来；旧结果按原方法回读，不能在 History 里偷偷用新公式重算。选择哪种数值表示之前，先找到第一次丢精度的地方，再决定哪些真实消费路径需要迁移。

## 七、怎样验证，而不夸大结论

最小回归集应该包括：137 × 0.015 的 exact/rounded/residual、负数 tie、CNY/USD 加法拒绝、同基金份额×净值的显式绑定、错基金绑定拒绝、1.00 与 0.999 的精确比较、极小非零值，以及目标权重不可行案例。

固定字符串和期望输出可以证明这些局部机制，但不能据此宣称真实基金收益口径、投资建议、交易或所有历史数字都已经正确。

## 结语

Numeric 的强保证不是“所有 Agent 数字都正确”，而是：**给定合法十进制输入、单位绑定和舍入政策，运算可复算，残差可解释，非法操作被局部拒绝。** 金融领域继续负责方法、依据、适用性与授权，精确数学才不会越权成为投资真值。
