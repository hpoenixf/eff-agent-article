# 多 Agent 值不值得开？我们测了启动、送达和最终收益

同一道题，主 Agent 真正派了子 Agent，答案会更好吗？2026 年 11 月 16—17 日，我们对照了 **100 次实际启动子 Agent** 的运行和对应的无子 Agent 运行，又单独比较了 **19 次实际收到 Reviewer 建议** 的运行。下面直接看分数和开销。

## 普通子 Agent 实际启动的 100 次

首轮有 13 次由主 Agent 自行启动子 Agent。对首轮没有委派的另外 87 个题次，我们加上明确的委派要求重跑，87 次都实际启动了子 Agent。每次都与同一题、同一重复编号、未启动子 Agent 的运行配对。

| 实际启动方式 | 运行对数（有效评分） | 启动均分／16 | 未启动均分／16 | 分差 | 胜／平／负 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 主 Agent 自行委派 | 13（13） | 11.08 | 13.92 | −2.85 | 6／1／6 |
| 明确要求委派后重跑 | 87（86） | 14.83 | 15.24 | −0.42 | 29／30／27 |

100 次实际启动的运行合计用了 **2,523 次**研究模型调用，对应的 100 次未启动运行用了 **1,111 次**。首轮为 521 对 188 次，补测为 2,002 对 923 次。

补测时，每个题次的三份答案放在同一次盲评中。表中未启动列对应同题的关闭组。同场参与评分的首轮未委派答案平均 **15.16 分**，比补测中实际委派的答案高 **0.34 分**。补测有 1 对没有有效评分，调用仍计入 87 对的实际消耗。

测评使用十道冻结的合成资料题，每题重复十次。评审模型只看问题、资料和匿名答案，从正确性、覆盖、限制和完成度四项打分，满分 16 分。两轮分开列分。

### 委派前，主 Agent 读到资料了吗？

首轮 13 次实际委派里，9 次是在主 Agent 还没读到可用正文时启动子 Agent，最后平均 **9.00 比 13.67**。主 Agent 已发出 11 至 20 次模型请求，部分子 Agent 接手后又遇到相同的读取问题。它们能把受阻原因带回去，有些答案也据此交代了限制，但题目需要的时间线或数值仍没做出来。

另外 4 次是在主 Agent 已读到五份来源后，把计算或统计交给子 Agent 复核。这 4 对平均 **15.75 比 14.50**，高 **1.25 分**，调用增加约 **42.6%**。

## Reviewer 建议实际送达的 19 次

Reviewer 的任务是检查已有研究的遗漏、冲突和薄弱假设。这组测试里有 19 次确认审查建议进入了主 Agent 的后续输入。下表用同一题、同一重复编号、没有 Reviewer 的答案做对照。

| 指标 | 实际收到建议 | 同题无 Reviewer | 差异 |
| --- | ---: | ---: | ---: |
| 平均分／16 | 13.21 | 13.68 | −0.47 |
| 平均整轮结束时间 | 306.59 秒 | 258.38 秒 | +48.21 秒（+18.7%） |
| 研究模型调用总数 | 477 | 246 | +231 次 |

19 对里，收到建议的一侧 **4 胜、7 平、8 负**。

一道扣除非经常性损益的题，收到建议后答了 **15 分**，对照是 **12 分**。高分答案把几种利润口径分得更清楚，也保留了实际缺失的拆分信息。另一道时间线题，收到建议的一侧只覆盖五份来源中的一份，得了 **9 分**，对照是 **16 分**。

## 下次增加一个 Agent，先说清它要改变什么

这些结果没有否定独立上下文和并行研究的价值。我们的实验用的是冻结的合成资料，仍存在资料导航和运行续接问题；它没有覆盖广泛网络探索，也没有评估不同模型组合，更没有识别各项意见的独立因果贡献。

任务差异尤其重要。Anthropic 在 [How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system) 中，把多 Agent 的优势与可并行探索的独立方向联系起来，同时讨论了额外 token 消耗和共享上下文、任务依赖带来的限制。它们的内部任务、模型组合和评估方式与本文不同，结果不能直接横比。这提醒我们继续问：任务到底需要更大的探索范围，还是只需要把已有材料读准确？

根据这次观察，我会把委派问题写得更具体一些。

如果主 Agent 已拿到资料，需要检查费用适用条件、复算一组数字或寻找某条结论的反例，可以给子任务明确的核验对象和可检查产物。只有一句“再看看有没有问题”，就很难分清它补上了缺口，还是复述了一遍已有结论。

如果主 Agent 卡在资料入口，先查实际可用的导航和读取回执。Child 可能帮助定位，但必须观察它是否获得了可用的新证据；不能因为任务交出去了，就把原来的阻塞视为已解决。

后来沿实际请求检查这些读取问题时，我们发现系统掌握了文件位置，但发给模型的目录省略了它。单片段材料的定位入口已经修通，对真实回答的影响还有待复测。[资料明明在，Agent 为什么读不到？](agent-document-navigation-after-empty-search.md)

评估 Reviewer 时，可以先看建议是否进入了主 Agent 的后续输入，再逐题核对最终答案补上了什么。上面两道题的分差，就分别落在利润口径和材料覆盖上。

**能启动专家，说明系统具备协作能力；是否值得启用，要看它是否提供新的证据、独立核验或有效反证，被主 Agent 用上，并改善了值得改善的结果。** 时间、token 和未知费用，也都属于这个判断。

下次增加一个角色之前，先选一条希望它改善的关键结论。沿实际输入、子任务发现和最终答案核对一遍，再与关闭该角色的结果比较。这样才能知道，额外的协作究竟帮了谁、帮在哪里，以及这份帮助值不值得。
